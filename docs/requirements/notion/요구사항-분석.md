# 요구사항 분석 — (울산 CLX) 체선료 최적화 Agent

- 작성일: 2026-11-04 · 상태: **초안** (팀·멘토 확인 전)
- 근거: 과제 원문(`official-brief.md`) 하나뿐이다. 현업 확인과 평가 기준은 아직 없다.
- 이 문서가 **요구사항 분석 문서**다. 원문을 받기 전에 쓴 PRD 초안(`03-prd-v0.md`)과 PRD 6칸(`06-prd-6cells.md`)은 이 문서를 기준으로 다시 고친다.
- 기호: R = 해야 하는 일, C = 지켜야 하는 조건, X = 하지 않는 일, Q = 모르는 것. "원문 3절 기능 1"은 원문의 그 부분이다.

## 1. 한 장 요약

- **만드는 것**: 선박 스케줄러가 울산 터미널의 대기 선박과 부두 조건을 넣으면, 예상 체선료를 근거와 함께 계산하고, 접안 순서를 여러 방안으로 시뮬레이션해 체선료가 낮은 후보를 남은 리스크와 함께 비교해 주는 Agent다. 고른 후보로 메일과 보고서 초안까지 만든다.
- **왜 필요한가**: 접안 순서를 숙련자의 감각으로 짜고 있고, 따질 조건이 많고, 여러 안을 빨리 견주기 어렵고, 체선료는 금액이 크며 분쟁으로 이어질 수 있다.
- **쓰는 사람**: 선박 스케줄러, 입출항 작업 지시자, 체선 지불 부서.
- **꼭 할 일 7가지**(R1~R7): 입력, 예상 체선료 계산, 후보 비교, 기준안 비교, 남은 리스크·대안, 보고서 초안, 계산과 제안 검증.
- **하지 않는 일**: 사내 시스템 실시간 연동, Agent의 자동 확정. 최종 접안 계획은 사람이 고른다.
- **아직 모르는 것 12가지**(Q1~Q12). 먼저 물을 것은 평가 기준과 마감, ML을 쓰는 곳, 받을 수 있는 자료, 예상 작업 종료 시간이다.

## 2. 사용자

| 사용자 | 하는 일 | 이 Agent에서 보는 것 |
|---|---|---|
| 선박 스케줄러 | 대기 선박과 부두 상황을 넣고, 후보를 비교해 최종 계획을 고른다 | 후보 비교 화면 (R1~R5) |
| 입출항 작업 지시자 | 고른 계획을 보고 입항과 출항 작업을 준비한다 | 선택한 계획, 남은 리스크, 주의할 점 (R5, R6) |
| 체선 지불 부서 | 선박별 예상 체선료와 근거를 미리 보고, 크게 날 가능성과 분쟁 위험을 점검한다 | 선박별 근거 (R2), 위험 점검 (R10, 기준 없음) |

## 3. 해야 하는 일

### 3-1. 꼭 필요한 일

원문 3절의 "최소 구현 기능" 다섯 가지와, 그것이 돌아가는 데 필요한 입력이다.

| 번호 | 해야 하는 일 | 맞았는지 확인하는 방법 | 원문 |
|---|---|---|---|
| R1 | 스케줄러가 대기 선박과 부두 상황을 넣을 수 있다. 입력에는 선박 도착 일시, 계약 정보, 하루 체선료, 일기예보, 생산·출하 계획, 선박·부두 제원, 부두별 접안 가능 제품, 일출·일몰, 조석, 현재 접안 중인 선박, 탱크·설비 제원이 들어간다 | 부두 2~3곳과 선박 몇 척짜리 가상 시나리오를 입력하거나 불러와 끝까지 돌릴 수 있다 | 개요, 1절, 2절 |
| R2 | 선박 하나를 고르면 체선 시간과 예상 체선료가 계산되고, 도착 일시·허용 시간·예상 작업 종료 시간·하루 체선료와 쓴 규칙이 근거로 함께 나온다 | 손으로 계산한 정답과 같다. 선박별로 일치 여부를 센다 | 3절 기능 1 |
| R3 | 접안 순서를 여러 방안으로 돌려 보고, 제약(부두별 접안 가능 제품, 조석, 일출·일몰, 기상)을 지키는 후보를 총 예상 체선료 낮은 순으로 나란히 보여 준다. 부두별 타임라인에서 선박을 누르면 R2의 근거가 나온다 | 모든 후보에서 제약 위반이 0건이고, 후보의 총 예상 체선료가 R2 계산의 합과 같다 | 3절 기능 2, 4절 |
| R4 | 도착 순서대로 접안한 기준안도 같은 방식으로 계산해 후보와 나란히 보여 준다 | 시나리오마다 후보가 기준안보다 얼마나 줄였는지 숫자로 나온다 | 3절 기능 5 |
| R5 | 후보마다 반영하지 못한 변수(날씨 급변, 설비·탱크 제약, 긴급 출하, 현장 안전 등)를 남은 리스크로, 대안과 주의할 점과 함께 붙인다. "지금 확정"이라고 하지 않고 담당자가 후보를 골라 확정한다 | 모든 후보에 리스크가 적혀 있거나 "없음"이 보인다. 화면에 확정 기능은 없고 선택만 있다 | 3절 기능 3 |
| R6 | 고른 후보로 메일과 보고용 Report 초안을 만든다. 왜 이 안인지, 무엇이 남았는지를 담는다 | 초안의 금액과 시각이 화면과 같고, 근거 없는 문장이 없다 | 3절 기능 4, 4절 |
| R7 | 손계산 정답과 자동 계산이 맞는 비율, 시나리오별 기준안 대비 총 예상 체선료 차이, 제약 위반 여부를 표로 보여 준다 | 발표에서 표 한 장으로 보여 줄 수 있다. 정답 세트와 시나리오는 팀이 만든다 | 3절 기능 5, 4절 |

### 3-2. 원문이 권하는 일

원문 6절 "진행 가이드"의 "고려할 점"이다. 필수라고는 쓰지 않았지만 평가에서 볼 가능성이 높다.

| 번호 | 해야 하는 일 | 맞았는지 확인하는 방법 | 원문 |
|---|---|---|---|
| R8 | 후보마다 어떤 입력(도착 일시, 일기예보 등)에 기대는지, 그 값이 바뀌면 순서가 달라지는지를 남은 리스크로 보여 준다 | 입력 하나를 바꾸면 순서가 달라지는 후보에 표시가 뜬다 | 6절 |
| R9 | 허용 시간을 언제부터 세는지, 기상 악화나 부두 사정으로 기다린 시간을 빼 주는지 같은 규칙을 코드에 박지 않고 계약 정보에서 읽는다. 어떤 규칙을 썼는지 근거에 보인다 | 계약 정보를 바꾸면 같은 선박의 결과가 바뀌고, 근거에 바뀐 규칙이 보인다 | 6절 |

## 4. 지켜야 하는 조건

- **C1**: 결과는 판단을 돕는 자료다. 최종 접안 계획은 사람이 고른다. (1절, 3절 기능 3, FAQ)
- **C2**: 정답 하나만 내지 않는다. 후보 여러 개와 남은 리스크, 대안을 함께 낸다. (FAQ)
- **C3**: 후보는 제약을 지킨다. 부두별 접안 가능 제품, 조석, 일출·일몰, 기상이다. (3절 기능 2)
- **C4**: 모든 금액에 근거가 붙는다. 왜 그 순서인지 다른 사람이 같은 기준으로 다시 따져 볼 수 있어야 한다. (1절, 3절 기능 1, 6절)
- **C5**: 데이터는 주관 팀 자료를 첫 멘토링에서 확인한다. 그 전에는 일기예보, 조석, 일출·일몰은 공공데이터포털에서 받고 나머지는 가상으로 만든다. (5절, FAQ)
- **C6**: 정답과 시나리오는 팀이 직접 만든다. 손계산 사례와 비교용 시나리오를 초반에 만든다. (3절, 6절)
- **C7**: 진행 순서는 부두 2~3곳과 선박 몇 척으로 줄인 가상 데이터로 계산, 비교, 리스크, 보고서까지 한 번 끝까지 잇고, 제약과 변수를 하나씩 더하는 것이다. (6절)
- **C8**: 기술은 팀이 고른다. 체선료 계산 규칙, 접안 순서 최적화, 시뮬레이션, 보고서를 나눠 맡는 Agent를 엮는 구성이다. (5절)
- **C9**: 데모는 기상 악화가 예보된 날 선박 여러 척이 몰리는 상황에서 후보 비교, 하나 선택, 보고서 초안까지 이어지는 흐름이다. (4절)

## 5. 하지 않는 일

- **X1**: 사내 시스템에서 실시간으로 데이터를 받아 오는 연동. (6절)
- **X2**: Agent가 접안 계획을 스스로 확정하는 기능. 사람이 고른다. (6절)

## 6. 모르는 것과 질문

설계가 막히는 순서대로 적었다. 1~4번이 먼저다. 누구에게 어떤 순서로 물을지와 보낼 글은 질문 정리 문서(`08-questions.md`)에 묶어 두었다. "현업 멘토"는 주관 팀 현업 담당자(격주 1회 대면), "교수님"은 전담 멘토(언제든)다.

| 번호 | 질문 | 왜 필요한가 | 누구에게 |
|---|---|---|---|
| Q1 | 평가 기준과 마감일은? 발표에서 무엇을 보고 평가하나? 요구사항 분석 단계에서 낼 문서의 양식이 있나? | 성공 기준, 일정, 문서 모양의 기준이 된다 | 교수님, 교육 담당 |
| Q2 | 핵심 기술에 ML이 있다. 어디에 쓰나? 꼭 써야 하나? 남은 리스크 문구는 규칙으로 만드나, AI가 쓰나? 기술 제한(웹 화면 등)이 있나? | 평가 기대와 구성이 달라진다 | 교수님 |
| Q3 | 주관 팀이 줄 수 있는 자료는? (실제 접안 이력, 계약 샘플, 선박·부두 제원, 비식별 여부) | 가상 데이터를 얼마나 만들지, 정답을 어떻게 만들지 정한다 | 현업 멘토 |
| Q4 | 예상 작업 종료 시간은 입력인가, 계산인가? 계산이면 무엇으로 하나? (하역 물량, 펌핑 속도, 탱크) 접안·호스·이안에는 보통 얼마나 걸리나? | 예상 체선료의 가장 큰 입력이고, 이 시간들이 다르면 같은 상황도 금액이 달라진다 | 현업 멘토 |
| Q5 | 기준안(도착 순서대로 접안)은 정확히 무엇인가? 제약 때문에 도착 순서를 못 지킬 때는? | 줄인 금액을 재는 기준이다 | 현업 멘토 |
| Q6 | 규모는? 한 번에 보는 기간, 선박 수, 부두 수, 후보 수 | R11의 방식과 화면 크기를 정한다 | 현업 멘토 |
| Q7 | 지불 부서가 보는 "크게 날 가능성"과 "분쟁 위험"은 무엇을 기준으로 하나? | R10을 정할 수 있다 | 현업 멘토 |
| Q8 | 계약은 몇 가지 유형을 다뤄야 하나? 허용 시간 시작 기준과 대기 시간 공제는 어떤 경우들이 있나? | R9의 범위다 | 현업 멘토 |
| Q9 | 보고용 Report와 메일에 정해진 양식이 있나? (받는 사람, 언어, 분량) | R6을 정할 수 있다 | 현업 멘토 |

## 7. 화면과 요구의 대응

원문 4절의 "최종 산출물 이미지"를 그린 와이어프레임이 별도 파일 `wireframe.html`이다. 금액과 시간은 자리 표시용 예시다.

| 화면 | 들어 있는 요구 |
|---|---|
| 접안 스케줄 비교 | R1 입력, R2 근거, R3 후보와 타임라인, R4 기준안, R5 리스크·대안, R8 입력 의존 표시 |
| 보고서 초안 | R6 |
| 검증 결과 | R7 |

그리면서 새로 나온 질문은 Q2, Q4, Q5, Q6, Q10이다. 화면에 어떤 숫자를 놓을지 정하다 보니 원문이 말하지 않은 것이 드러났다.

## 8. 이미 있는 것

코드와 문서에서 확인한 것만 적는다. 원문 기능과 하나씩 대조하는 일은 다음 단계다. 모든 데이터는 가상이다.

- `clock/`: 레이타임 계산 엔진. 계산서 줄마다 근거(룰 ID, SOF 행)가 붙고, 골든 케이스 7개가 정답과 일치하며 테스트 122개가 통과한다. R2의 계산과 근거에 해당한다.
- `prototype/engine/sim.py`: 선석별 순서와 환경(도착 예정, 풍속, 부두 제약)으로 접안과 하역을 예측하고, 그 위에 계산을 얹어 예상 체선료를 낸다. 제약은 조석, 파고, 시정, 탱크, 배관, 예선, 제품 전환 등 16종이다. R2의 예상 계산과 R3의 제약에 해당한다.
- `prototype/engine/optimize.py`: 제약을 지키면서 예상 체선료 합이 작은 접안 순서를 찾는다. 6~9척은 완전 탐색이다. 프로토타입 시나리오 17개에서 "현업 규칙"과 비교한 숫자가 있다. R3과 R4에 해당한다.
- `prototype/engine/drafts.py`: 메일과 메모 초안. R6의 일부다. 보고용 Report 형식인지는 확인하지 않았다.
- `prototype/engine/assurance.py`, `golden.py`: 검증 지표와 정답 케이스. R7의 일부다.
- 웹 화면, HTTP API, MCP 서버가 있다. 자세한 것은 `prototype/README.md`다.

프로토타입이 기준으로 삼는 "현업 규칙"은 선종별 선착순(FCFS)이다. 원문의 기준안은 "도착 순서대로"라서 거의 같지만, 같은 정의인지는 Q5에서 확인한다. 원문 6절의 "먼저 할 것"(한 흐름 관통, 계산 규칙과 정답 세트)을 풀이하고 정답 세트를 시작한 것은 `09-first-steps.md` 문서다. SC-01 한 사례에서는 프로토타입의 최적화도 손계산 정답과 같은 순서를 골랐다.
