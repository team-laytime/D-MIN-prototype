## 1. 어떻게 나눴나

**기능과 비기능을 가른 기준**

- **기능(FR)**: 데모 흐름 `조건 입력 → 계산 → 후보 비교 → 리스크 → 선택 → 보고서 → 검증`에서 사용자가 하는 일, 받는 결과. 빼면 화면에서 할 수 있는 일이 하나 사라진다.
- **비기능(NFR)**: 그 일을 얼마나 정확하게, 근거 있게, 안전하게, 빠르게, 싸게 하는지. 빼도 할 일은 그대로인데 결과를 믿을 수 없게 된다. 캔버스의 '해결하려는 문제'와 '제약조건'에서 나왔다.

**캔버스를 요구사항으로 옮긴 방법**

- MVP 4개와 포함 범위 → 기능 요구사항
- 성공기준 3개 → 수용기준(숫자로 쪼갬)
- 해결하려는 문제·제약조건·운영 방식 → 비기능 요구사항
- 제외 범위 → 표에 넣지 않음 (5절)

**우선순위**

- **Must**: 캔버스 MVP와 성공기준을 지키는 데 빠지면 안 되는 것
- **Should**: 포함 범위나 원문이 권하지만, 없어도 데모 흐름은 끝까지 도는 것
- **Could**: 시간이 남으면 하는 것

개수: 기능 16 (Must 13 · Should 2 · Could 1), 비기능 9 (Must 4 · Should 4 · Could 1).

**용어 '시나리오'**: 표에서 두 뜻으로 쓰인다. 하나는 검증·데모용 상황(FR-01, FR-07, FR-10, NFR)이고, 다른 하나는 최적화로 나온 접안 일정 한 안(FR-00, FR-02-1, FR-13)으로 '후보'와 같은 뜻이다. 팀에서 하나로 정하면 표 문구를 맞춘다.

| FR-10 | 포함 범위 "정답 세트·검증 시나리오", "검증 결과표", 성공기준 ①②, 원문 기능 5 | 발표에서 이 표 한 장으로 성공기준 ①②를 보여 준다 |

| FR-12 | 제안 솔루션 "멀티 Agent" (MVP 밖) | 프로토타입의 조회 전용 도구로 할 수 있다. 시간이 남으면 한다 |
| FR-13 | 팀원 추가 (11-09) | 접안 일정이 정해진 FIX 선박은 순서를 바꾸는 대상에서 빼고, 접안 시각을 고정값으로 둔다 |

## 4. 팀이 정할 숫자

표에 넣은 숫자 중 아래는 **제안 값**이다. 팀이 정하면 표와 이 줄을 같이 고친다.

- **부두 3곳·선박 8척** (FR-01, NFR-06): 캔버스 포함 범위의 "선박 ○척"과 맞춘다. 8척은 수리계획법 예제(`journeys/`, 선석 3개)에서 이미 돌려 본 규모다.
- **후보 3개** (FR-04)
- **±6시간** (FR-07)
- **30초, 1분** (NFR-06)
- **1회 1달러** (NFR-07)
- **2명, 10분** (NFR-09)

## 5. 넣지 않은 것

캔버스 제외 범위라서 표에 넣지 않았다.

- 사내 시스템 실시간 연동
- Agent의 접안 계획 자동 확정 (반대로 FR-08이 "사람이 확정"을 요구사항으로 고정한다)
- 실제 선박에 대한 도착 시각 요청·감속 협상
- 항차 종료 후 SOF 기반 체선료 정산·클레임 검토
- 도착 시각·작업 시간 예측 모델 고도화 (FR-01은 입력값이나 단순 추정만 쓴다)

양식의 예시 "모바일에서도 화면이 깨지지 않는다"도 넣지 않았다. 사용자 3역(선박 스케줄러, 입출항 작업 지시자, 체선 지불 부서)이 모바일로 본다는 근거가 아직 없다. 필요하면 Could로 더한다.

## 6. 문서에 넣기 전에

- 문서 맨 아래 '제출 전 확인'에 **페이지 수 제한**이 있다. 몇 쪽인지는 문서에 없다. 넘치면 Could(FR-12, NFR-09)부터 뺀다.
- **팀원 전체 확인·검토**가 조건이다. 우선순위와 4절 숫자는 팀 합의로 바꾼다.
