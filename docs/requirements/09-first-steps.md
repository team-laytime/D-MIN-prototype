# 먼저 할 것 두 가지 — 한 흐름 관통, 계산 규칙과 정답 세트

- 작성일: 2026-11-04 · 근거: 과제 원문 [`official-brief.md`](official-brief.md) 6절 "진행 가이드"의 "먼저 할 것" 두 줄
- 이 문서는 세 가지를 한다. 두 줄의 뜻과 이유를 풀이하고, 우리가 가진 정답이 무엇인지 정리하고, 비어 있던 정답을 채우는 첫 작업(SC-01)을 시작한다.
- 이유는 두 종류로 나눠 적었다. "원문"은 원문에 직접 쓰인 말이고, "추론"은 원문의 다른 문장과 맞춰 본 우리 생각이다. 원문은 이 두 줄의 이유를 길게 적지 않았다.
- 정답이란 손으로 계산해 둔 기준 답이다. 프로그램이 낸 값과 맞는지 비교하는 데 쓴다.

## 1. 원문이 말한 것과 이유

### 1-1. 한 흐름 관통

원문: "부두 두세 곳과 선박 몇 척으로 줄인 가상 데이터로 체선료 계산, 후보 비교, 리스크 표시, 보고서 초안까지 처음부터 끝까지 한 번 이어요. 제약과 변수는 그 위에 하나씩 더해요."

쉬운 말: 문제를 작게 줄여서 입력부터 보고서까지 끝까지 한 번 먼저 통과시키고, 제약은 그 위에 하나씩 얹으라는 뜻이다.

왜 그렇게 적었나:
- 원문: 제약과 변수는 "하나씩" 더한다. 한꺼번에 넣지 말라는 말이다.
- 추론: 입력이 열 가지가 넘고 기능이 다섯 개다(원문 3절). 부분을 따로 완성했다가 마지막에 잇는 방식은 연결이 안 맞을 위험이 크다. 얇게라도 끝까지 이으면 연결 문제가 초반에 드러난다.
- 추론: 제약이 네 종류다(부두별 접안 가능 제품, 조석, 일출·일몰, 기상). 한꺼번에 넣고 결과가 틀리면 원인을 찾지 못한다. 하나씩 넣으면 "방금 넣은 것 때문"이라고 말할 수 있다.
- 추론: 규모를 줄이면 가상 데이터와 손계산 정답을 만드는 일도 작아진다. 실제 자료를 받기 전에는 이게 현실적이다(원문 5절). 발표에서도 끝까지 도는 모습이 먼저 있어야 한다(원문 4절 데모 예시).

### 1-2. 계산 규칙과 정답 세트

원문: "체선 시간 계산 규칙을 먼저 글로 정리하고, 손으로 계산한 선박 사례와 비교용 시나리오를 초반에 만들어 두면 개발하는 동안 계속 결과를 확인할 수 있어요."

쉬운 말: 규칙을 글로 먼저 쓰고, 손으로 푼 답을 미리 만들어 두면, 코드를 고칠 때마다 맞는지 확인할 수 있다는 뜻이다.

왜 그렇게 적었나:
- 원문: "개발하는 동안 계속 결과를 확인할 수 있어요." 원문이 직접 적은 이유다.
- 원문 3절 기능 5: 발표에서 "손으로 계산한 정답 세트와 자동 계산이 맞는 비율"과 "기준안보다 줄인 금액"을 보여 줘야 한다. 정답이 없으면 이 지표를 낼 수 없다.
- 원문 3절: 주관 팀 자료를 받기 전에는 "정답을 붙인 검증 시나리오를 직접 만들어야" 한다. 팀이 정답의 출처다.
- 원문 6절: 계약마다 규칙이 다르니 코드에 박지 말고 계약 정보에서 읽으라고 했다. 규칙을 글로 먼저 정리해야 무엇을 바꿔 끼울 수 있게 만들지 보인다.
- 추론: 정답을 "손으로" 구하라는 것은 자동 계산과 독립된 방법으로 구해야 검증이 되기 때문이다. 같은 코드가 낸 값을 정답으로 쓰면 틀려도 모른다.
- 추론: "비교용 시나리오"가 따로 있는 것은 후보 비교의 정답(어느 순서가 더 낮은가)이 한 척 계산으로는 나오지 않고, 여러 척이 부두를 나눠 쓰는 상황이 있어야 나오기 때문이다.

### 1-3. 두 줄은 한 몸이다

끝까지 이은 흐름은 "돌아간다"만 알려 주고, 정답 세트는 "맞게 돌아간다"를 알려 준다. 그래서 한 흐름을 돌릴 때마다 정답 세트로 확인하라는 뜻으로 읽는다.

## 2. 계산 규칙 (글)

근거는 [`docs/domain/04-worked-examples.md`](../domain/04-worked-examples.md) 0절의 템플릿과 `clock/` 엔진이다.

1. 선박이 도착해서 NOR(준비 완료 통지)를 낸다. 도착 전에 낸 NOR은 무효로 보고 쟁점으로 표시한다.
2. 레이타임 개시는 "NOR 수령 + 통지시간(6시간)"과 "접안 완료(all fast)" 중 더 이른 시각이다. (ASB-06-NOR-START)
3. 레이타임 종료는 호스 분리 시각이다. (ASB-11-END-HOSES)
4. 경과 시간은 종료에서 개시를 뺀 값이다.
5. 공제할 시간을 뺀다. 이동(shifting) 시간과 선박 책임(펌핑 보증 미달 등) 시간이다. (ASB-07-SHIFTING-EXCL, RIDER-PUMPING) 체선에 들어간 뒤의 이동은 공제하지 않는 것이 기본이다(once on demurrage). 다만 용선주가 공제를 주장할 수 있어 쟁점으로 표시한다.
6. 사용 시간은 경과에서 공제를 뺀 값이다. 체선 시간은 "사용 시간 − 허용 시간"이고 0보다 작으면 0이다. 허용 시간은 계약에 적힌 값이다.
7. 체선료는 "전액 시간 × 하루 요율 ÷ 24 + 반액 시간 × 하루 요율 ÷ 48"이다. 반액은 체선 중 기상 중단 같은 경우다. (ASB-08-HALF-RATE)
8. 시간은 분 단위, 금액은 센트까지 계산한다. 정답과 비교할 때만 달러로 반올림한다.
9. 해석이 갈리는 곳(체선 중 이동, 야간 대기의 부담 주체 등)은 판정하지 않고 "담당자 확인 필요"와 두 가지 계산을 함께 낸다.

허용 시간, 하루 요율, 통지시간은 코드에 박지 않고 입력의 `contract_terms`에서 읽는다. 원문 6절의 "계약 정보에서 읽게 하라"에 해당한다.

"예상" 계산도 규칙은 같다. 도착, 접안, 작업 종료 시각을 예측해서 같은 규칙에 넣을 뿐이다. 후보 비교는 접안 순서마다 선박별 체선료를 같은 규칙으로 구해 합하는 일이다.

## 3. 정답이 뭐가 있나

### 3-1. 이미 있는 정답: 한 척 계산 (TC 7개)

| TC | 보는 규칙 | 체선 시간 | 정답 금액(USD) |
|---|---|---|---|
| TC-01 | 개시 = min(NOR+6h, 접안) | 0 | 0 |
| TC-01b | 개시 뒤 이동 공제 | 3시간 30분 | 17,500 |
| TC-02 | 대기 산입, 이동 공제 | 3시간 | 6,875 |
| TC-03 | 묘박지에서 체선 돌입, 체선 중 이동, 반액 | 40시간 30분 | 187,500 (대안 177,500) |
| TC-04 | 펌핑 보증 미달 공제 | 0 | 0 (공제가 없으면 7,292) |
| TC-05 | 무효 NOR | 0 (선주 주장 3시간 30분) | 0 (선주 청구 3,792) |
| TC-05b | 무효 NOR 뒤 재제출 | 1시간 30분 | 1,625 |

원문은 [`docs/domain/04-worked-examples.md`](../domain/04-worked-examples.md)의 "테스트 케이스 요약"이다. 손으로 따라 계산하도록 쓴 것이고, 계산 엔진 `clock/`이 7개 모두 같은 값을 낸다.

성격: 사건 기록(SOF)이 다 있는 지난 일 기준이다. 원문이 요구하는 "예상 체선료"와 "후보 비교"의 정답은 아니다.

### 3-2. 숫자는 있지만 손계산 정답은 아닌 것: 프로토타입 시나리오

프로토타입 시나리오(6척, 4선석)에는 기준 계획 노출 $167,800, 폭풍 예보로 +$74,242, 현업 규칙 $251,750에서 에이전트 승인 $108,742 같은 숫자가 있다. 엔진이 계산하고 테스트가 그 값을 고정해 둔 것이다. 손으로 따로 검산했다는 기록은 찾지 못했다. 그래서 정답이라기보다 "지금 엔진이 내는 값"이다.

### 3-3. 이번에 만든 정답: SC-01 (두 척, 한 부두)

**조건 (단순화)**: 부두 하나를 X선과 Y선이 나눠 쓴다. 앞 배가 D1 06:00에 부두를 비운다. 접안(all fast)은 비운 1시간 뒤, 호스 연결과 양하 개시는 접안 1시간 뒤(같은 시각), 호스 분리 1시간 뒤 이안이 끝나 다음 배가 들어간다. 이동, 반액, 펌핑 공제는 없고 접안 시간 제약도 없는 소형선이다. 이 시간들이 "시간 가정"이고, 이 정답은 이 가정 아래에서만 정답이다.

| | X선 | Y선 |
|---|---|---|
| NOR 수령 | D1 02:00 | D1 04:00 |
| 허용 시간 | 24시간 | 12시간 |
| 하루 요율 | 48,000 (시간당 2,000) | 96,000 (시간당 4,000) |
| 양하 시간 | 14시간 | 8시간 |

**순서 A: 도착 순서 (X 먼저)**

| | X선 | Y선 |
|---|---|---|
| 접안 완료 | D1 07:00 | D2 01:00 |
| 호스 분리 | D1 23:00 | D2 11:00 |
| 레이타임 개시 | D1 07:00 (접안이 먼저) | D1 10:00 (NOR + 6h) |
| 사용 시간 | 16시간 | 25시간 |
| 체선 시간 | 0 (허용 24시간) | 13시간 (허용 12시간) |
| 체선료 | 0 | 13 × 4,000 = 52,000 |

순서 A의 합계는 52,000이다.

**순서 B: Y 먼저**

| | X선 | Y선 |
|---|---|---|
| 접안 완료 | D1 19:00 | D1 07:00 |
| 호스 분리 | D2 11:00 | D1 17:00 |
| 레이타임 개시 | D1 08:00 (NOR + 6h) | D1 07:00 (접안이 먼저) |
| 사용 시간 | 27시간 | 10시간 |
| 체선 시간 | 3시간 (허용 24시간) | 0 (허용 12시간) |
| 체선료 | 3 × 2,000 = 6,000 | 0 |

순서 B의 합계는 6,000이다.

**정답**: 더 낮은 후보는 순서 B(Y 먼저)이고 총 6,000이다. 기준안(도착 순서)은 52,000이다. 줄인 금액은 46,000이고 제약 위반은 0건이다.

**왜 이런 답이 나오나**: 허용 시간이 짧고 요율이 높은 Y를 먼저 보내면, 허용 시간이 긴 X가 기다려도 체선이 조금만 생긴다. 반대로 하면 허용 시간이 짧은 Y가 기다리다 체선에 들어간다. 순서에 따라 금액이 이렇게 갈리기 때문에 "후보 비교"가 필요하다.

**검산**: 네 사례를 엔진에 넣어 위 숫자와 같은 값이 나왔다. 엔진이 A의 Y선과 B의 X선에서 "양묘 기록 없음(증빙 확인)" 안내를 낸다. 이동 시간을 0으로 둔 단순화 때문이고 금액에는 영향이 없다.
- 입력 파일: [`answers/`](answers/)의 `SC-01-A-X`, `SC-01-A-Y`, `SC-01-B-X`, `SC-01-B-Y` (`.json`)
- 매번 확인하는 테스트: [`clock/tests/test_sched_answers.py`](../../clock/tests/test_sched_answers.py). clock 테스트 128개가 통과한다.
- 직접 돌려 보기:

```bash
cd clock && python3 -m laytime ../docs/requirements/answers/SC-01-A-Y.json
```

**프로토타입 확인**: 같은 두 척을 프로토타입의 시뮬레이션과 최적화에 넣었다. 확인하는 테스트는 [`prototype/tests/test_sc01.py`](../../prototype/tests/test_sc01.py)이고, 프로토타입 테스트 186개가 통과한다.

| 시간 가정 | 순서 A (도착 순서) | 순서 B (Y 먼저) | 줄인 금액 | 최적화가 고른 순서 |
|---|---|---|---|---|
| SC-01과 같게 맞춤 | 52,000 | 6,000 | 46,000 | Y 먼저 |
| 프로토타입 기본값 | 58,000 | 6,000 | 52,000 | Y 먼저 |

- 시간 가정을 SC-01과 같게 맞추면(이동 0, 접안 60분, 호스 연결 60분, 양하 개시 0, 호스 분리 60분, 이안까지 60분, 선석 회전 0분) 프로토타입이 손계산과 같은 52,000과 6,000을 낸다. 선박별 값도 같다. 순서 A는 X 0, Y 52,000이고 순서 B는 Y 0, X 6,000이다. 프로토타입이 "현업 규칙" 기준안으로 잡는 순서도 도착 순서(X 먼저)다.
- 기본값으로 돌리면(2026-11-04 기준) 순서 A가 58,000이다. 프로토타입의 기본 시간(이동 90분, 접안 30분, 호스 연결 60분, 양하 개시 30분, 호스 분리 60분, 서류 60분, 이안 30분, 선석 회전 60분)이 SC-01의 가정과 달라서 Y가 더 오래 기다린다. 그래도 최적화가 고르는 순서는 같다.
- 그래서 정답은 시간 가정과 함께 적어야 한다. 같은 상황이어도 가정이 다르면 금액이 달라진다. 접안과 이안에 실제로 얼마나 걸리는지를 현업 멘토께 물어야 하는 이유다(질문 Q4).
- 확인하다가 한 번 어긋났다. 처음에는 가상 선박의 총톤수를 주간 접안 제한 기준(25,000)과 같게 두어서 야간 접안이 막혔고, 두 순서의 금액이 모두 커졌다. 제약이 제대로 동작한 것이고, 총톤수를 낮추자 일치했다. 이 경험은 SC-02(일출·일몰 제약)를 만들 때 그대로 쓸 수 있다.

모든 SC에는 "후보 목록에 제약 위반이 없다"도 정답으로 붙인다(R7). 남은 리스크 문구에는 숫자 정답이 없어서, "반드시 들어가야 할 항목"의 체크리스트로 확인한다.

## 4. 한 흐름 관통: 프로토타입은 어디까지 가나

원문의 한 흐름 단계를 프로토타입의 5분 데모([`usage.md`](../../prototype/docs/usage.md) 6절)와 맞춰 봤다.

| 원문의 단계 | 프로토타입 | 상태 |
|---|---|---|
| 입력 | 시나리오 데이터(6척, 4선석)는 JSON 파일을 고쳐서 바꾼다(`usage.md` 8절). 한 척 계산은 입력·계산기 화면에서 SOF를 넣는다 | 스케줄러가 화면에서 선박과 부두를 입력하는 폼은 없다 |
| 체선료 계산 | 기준 계획의 체선료 노출 $167,800과 최대 노출 선박이 나온다 | 있다 |
| 후보 비교 | 후보 카드에 예상 체선료, 선정 이유, Risk, 가정이 나온다. 현업 규칙과 최적화 결과를 견준다 | 있다 |
| 리스크 표시 | 후보 카드의 Risk와 가정 | 일부. 원문 R5의 항목(날씨 급변, 설비·탱크, 긴급 출하, 현장 안전)을 다 덮는지는 대조 전이다 |
| 보고서 초안 | 통보·회신·메모 초안(`drafts.py`) | 보고용 Report 형식인지는 확인하지 못했다 |
| 사람이 고름 | "이 옵션 적용" 승인, 계획 버전, 감사 로그 | 있다. 자동 확정은 없다 |
| 정답 확인 | TC 7개는 엔진이 일치한다. SC-01은 프로토타입의 최적화까지 같은 답을 낸다 | 6척 시나리오 숫자의 손계산 정답은 아직 없다 |

한 흐름은 프로토타입이 이미 거의 통과한다. 비어 있는 것은 입력 폼, 보고용 Report, 그리고 정답 확인이다.
