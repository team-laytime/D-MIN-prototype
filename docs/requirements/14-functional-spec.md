## 읽는 법

- 기능마다 **입력 → 처리 → 출력** 순서로 적었다. 처리의 번호가 순서다.
- **다른 길**은 다르게 가도 끝나는 경우, **멈춤**은 거기서 더 나아가지 않는 경우다.
- **완료 기준**은 요구사항서의 수용기준을 그대로 옮겼다.
- **[가정]** 은 요구사항서에 없어 채운 것, **[확인 필요]** 는 팀이나 멘토에게 물어야 하는 것이다.

## 계산 한 번의 안쪽

스케줄러가 계산을 누르면 도는 순서다. 이 안에서는 LLM을 부르지 않는다 (NFR-01).

1. 입력 검증 (FR-08) — 오류가 있으면 여기서 멈춘다
2. 들어갈 수 없는 부두 빼기 (FR-14 · FR-15) — 제원 5종, 화물 그룹
3. 기준안 만들기 (FR-41) — ETA 순서, 가장 이른 부두
4. 배정안마다 되풀이 (FR-42)
   - 움직이지 않을 선박 (FR-17 · FR-18) — FIX 고정, WORKING 점유
   - 제약마다 접안 가능시각 (FR-16·19·20·21·22·24) — 여섯 가지 시각
   - ETB = 가장 늦은 시각 (FR-27) — 바뀌면 다시 검사
   - 작업 시각 (FR-29 · FR-30) — 작업시작·완료, 호스분리, ETU
   - 안 되는 배정 거르기 (FR-17 · FR-23 · FR-25) — FIX 침범, 재고, 마감
   - 정박개시 → 정박종료 (FR-31 · 32 → FR-33 · 34) — Laycan, Daylight, Laytime
   - 기상 공제 → 체선료 (FR-35 → FR-36) — max(0, …) × 일 체선료 ÷ 24
   - USD 합계 (FR-37) — 배정안의 총 예상 체선료
5. 총액 낮은 순 최대 3개 (FR-42) — 후보끼리 1척 이상 다르게
6. 후보가 없으면 (FR-43) — '실행 가능한 후보 없음'과 위반 내역

```
체선료 = max(0, 호스분리 − 정박종료 − 기상 공제) × 일 체선료 ÷ 24
정박종료 = 정박개시 + Laytime
ETB = 제약별 접안 가능시각 가운데 가장 늦은 시각
```

접안 가능시각 여섯 가지

- FR-16 선행 선박: max(ETA + Direction, 선행 선박 ETU + Switching)
- FR-19 야간 도선: 걸리면 직후 08:00 (Last POB = 일몰 − 1.5시간 또는 − 2시간)
- FR-20 동일 화물 그룹: 조합 {#6,#7,#8} · {#1-1,#1-2,#2-7}: 접안 중 선박 ETU − 2시간
- FR-21 부두 동시 접안: #4-1 · #4-2: 접안 중 선박 ETU − 2시간 (둘 다 GRT 3,000톤 이하면 제외)
- FR-22 부두 사용 제한: 제한 종료 + Direction
- FR-24 조석: 조석 시간창 안으로 조정

## G1 준비 · 기준 데이터

- 단계: 준비 · 누가: 기준 정보 관리자 · 유스케이스: UC-01 · 02 · 03 · 18
- 계산이 읽을 기준값과 참고 데이터를 미리 넣어 둔다. 규칙을 코드가 아니라 데이터로 두는 자리다.
- 다음으로 넘기는 것: 기준 정보 테이블(버전) · 일출·일몰 시각 · 과거 실적

흐름

- **기준 정보**
  - 1. [기준 정보 관리자] 기준 정보 파일 등록 (FR-09)
  - 2. [시스템] 검사하고 버전 붙여 저장 (NFR-05)
    - 멈춤: 형식 오류 → 저장 안 함 [가정]
  - → 부두 거르기 · 접안 가능시각 · Daylight가 읽는다 (FR-14·15·16·19·20·21·32)
- **일출 · 일몰**
  - 1. [기준 정보 관리자] 일출·일몰 파일 적재 (FR-12)
  - 2. [시스템] 기간 안 날짜가 다 있는지 확인 (FR-12)
    - 다른 길: 없는 날짜 → 관련 계산 '미완료'
  - → 야간 도선 · Daylight 정박개시가 읽는다 (FR-19 · FR-32)
- **공공데이터**
  - 1. [기준 정보 관리자] 수집 시작 (FR-13)
  - 2. [공공데이터포털] 포털에서 일출·일몰, 조석, 기상 예보 받기 (FR-13)
    - 다른 길: 무응답 → 저장된 값 사용
  - → 출처 · 수집 시각과 함께 저장 (FR-13)
- **과거 실적**
  - 1. [기준 정보 관리자] 실적 파일 불러오기 (FR-10)
    - 다른 길: 출처가 SOF → LLM으로 추출 FR-11
  - 2. [시스템] 검사하고 저장 (FR-10)
  - → 작업시간 추정이 읽는다 (FR-30)

### FR-09 기준 정보 관리

- 우선순위: Must · 시작: 기준 정보 관리자 · 유스케이스: UC-01
- 부두·화물·규칙에 쓰는 기준값을 코드가 아니라 기준 정보 파일로 관리한다.

입력

- 부두 허용 제원 (최대 DWT, 최대·최소 LOA, 최소 PBL, 최대 Draft)
- 부두별 취급 화물 그룹, 자재코드 → 화물 그룹 매핑
- 부두별 Direction · Switching 시간
- 동시 접안 제한 조합, 야간 도선 기준, Daylight 적용 선종

처리

1. 관리자가 기준 정보 파일을 등록하거나 바꾼다
2. 형식과 빠진 항목을 검사한다 [가정]
3. 버전을 붙여 저장한다 (NFR-05)
4. 등록된 내용을 요약해 보여 준다

- 멈춤: 형식 오류 · 항목 누락 → 저장하지 않고 어느 항목인지 알려 준다 [가정]

출력

- 버전이 붙은 기준 정보 테이블
- → 부두 거르기 FR-14·15, 접안 가능시각 FR-16·19·20·21, Daylight FR-32

완료 기준: 울산 CLX의 제원, 화물 그룹, Direction·Switching 시간, 제한 조합이 등록되어 계산에 사용됨

관련: NFR-05 규칙 분리·버전 관리 (값만 바꿔 결과가 바뀌는 시연 2종) · NFR-06 규칙 ID 추적

### FR-12 일출·일몰 데이터

- 우선순위: Must · 시작: 기준 정보 관리자 · 유스케이스: UC-01
- 울산 기준 날짜별 일출·일몰 시각을 파일로 적재한다.

입력

- 날짜별 일출·일몰 시각 파일 (울산 기준)

처리

1. 파일을 적재한다
2. 입력 시나리오 기간의 모든 날짜에 값이 있는지 확인한다

- 다른 길: 값이 없는 날짜 → 그 날짜에 걸리는 계산을 '미완료'로 표시한다

출력

- 날짜별 일출·일몰 시각
- → 야간 도선의 Last POB FR-19, Daylight 정박개시 FR-32

완료 기준: 시나리오 기간의 모든 날짜에 값이 있음. 값이 없는 날짜의 관련 계산은 '미완료'로 표시됨

관련: 공공데이터로 받은 값(FR-13)으로 채울 수 있다 [가정]

### FR-13 공공데이터 연동

- 우선순위: Should · 시작: 기준 정보 관리자 · 외부 API · 유스케이스: UC-02
- 공공데이터포털 API에서 일출·일몰, 조석, 기상 예보를 받아 저장한다.

입력

- 날짜 범위, 지역(울산)
- 포털 API 키 (저장소가 아니라 환경변수·비밀 저장소, NFR-14)

처리

1. 수집을 시작한다
2. 포털 API에 일출·일몰, 조석, 기상 예보를 요청한다
3. 받은 값을 저장한다
4. 출처와 수집 시각을 표시한다

- 다른 길: API 무응답 → 전에 저장한 값을 쓰고 '저장된 값(수집 시각)'이라고 표시한다 (NFR-11)

출력

- 저장된 값 + 출처 + 수집 시각

완료 기준: 울산 기준 날짜 3개의 값이 포털 조회값과 같음

관련: [확인 필요] 수집을 사람이 시작하는지 자동인지, 조석·기상 값을 계산에 바로 넣는지

### FR-10 과거 작업 실적 입력

- 우선순위: Should · 시작: 기준 정보 관리자 · 유스케이스: UC-03
- 작업시간을 추정할 때 쓸 과거 작업 실적을 불러온다.

입력

- 과거 작업 실적 파일 — 선박코드, 자재코드, 부두, 작업 시작·종료, 작업량, 호스분리 시각
- 실데이터를 받기 전에는 가상 실적

처리

1. 정형 파일을 불러온다
2. 형식을 검사하고 저장한다
3. 적재한 건수를 보여 준다

- 다른 길: 실적의 출처가 SOF 문서 → FR-11로 추출해 적재한다

출력

- 과거 실적 테이블
- → 작업시간 추정 FR-30

완료 기준: 가상 실적 파일을 불러와 작업시간 추정에 사용함

### FR-11 SOF 추출·과거 실적 적재

- 우선순위: Could · 시작: 기준 정보 관리자 · LLM · 유스케이스: UC-18
- 과거 SOF 문서에서 실적 항목을 뽑아 과거 실적 형식으로 넣는다.

입력

- 과거 SOF 문서

처리

1. 관리자가 SOF 문서를 올린다
2. LLM이 작업 시작·종료, 작업량, 호스분리 시각을 추출한다
3. 정답 필드와 견준 정확도를 표시한다
4. 담당자가 확인한 건만 과거 실적 형식으로 적재한다

- 멈춤: 확인하지 않은 건 → 과거 실적에 반영하지 않는다

출력

- 과거 실적 행 (확인된 건만)
- → 과거 작업 실적 FR-10

완료 기준: 정답 필드 대비 정확도가 표시됨. 담당자가 확인한 건만 과거 실적에 반영됨

관련: NFR-01 LLM은 추출에만 · NFR-03 추출 일관성 · NFR-15 전송 데이터 제한

## G2 입력 · 문서

- 단계: 입력 · 누가: 선박 스케줄러 · LLM · 유스케이스: UC-04 · 05 · 15
- 계약 문서에서 뽑은 값을 사람이 확인하고, 선박·부두·재고와 함께 계산에 넣을 한 묶음(입력 시나리오)으로 만든다.
- 다음으로 넘기는 것: 확인된 계약 조건 · NOR Tender · 입력 시나리오

흐름

- **계약 문서**
  - 1. [선박 스케줄러] C/P · NOR 올리기 (FR-02)
    - 멈춤: 지원 안 하는 형식 → 거절
    - 다른 길: NOR 없음 → ETA로 계산
  - 2. [LLM] 필드 추출 (FR-03 · FR-04)
    - 멈춤: LLM 무응답 → '미추출', 직접 입력 [가정]
  - 3. [시스템] 원문 근거 붙이기 (FR-05)
    - 멈춤: 근거 없음 → '미추출'
  - 4. [시스템] C/P와 NOR 대조 (FR-07)
  - 5. [선박 스케줄러] 확인하고 고치기 (FR-06)
    - 멈춤: 미확인 값 남음 → 계산 못 함
- **입력 시나리오**
  - 1. [선박 스케줄러] 파일 불러오기 · 화면 입력 (FR-01)
  - 2. [시스템] 확인된 추출값을 계약 조건에 채우기 (FR-01)
  - 3. [선박 스케줄러] 값 고치고 저장 (FR-01)
  - 4. [시스템] 입력 검증 (계산을 시작할 때) (FR-08)
    - 멈춤: 오류 → 계산 시작 안 함, 선박·항목·사유 표시
  - → 계산으로 넘어간다 (G3 · G4 · G5)

### FR-02 문서 업로드

- 우선순위: Must · 시작: 선박 스케줄러 · 유스케이스: UC-04
- C/P와 NOR 문서를 올려 해당 선박·항차에 연결한다.

입력

- C/P, NOR 파일 (PDF · DOCX · TXT)
- 연결할 선박 · 항차

처리

1. 스케줄러가 선박·항차를 고르고 파일을 올린다
2. 파일 형식을 확인한다
3. 문서를 선박 ID와 연결한다
4. 필드 추출로 넘긴다 → FR-03·04

- 멈춤: 지원하지 않는 형식 → 사유와 함께 거절한다
- 다른 길: NOR이 없는 선박 → C/P만 올린다. 그 선박은 ETA로 계산된다 (FR-04)

출력

- 선박 ID에 연결된 C/P · NOR 문서

완료 기준: 목업 C/P·NOR 전체가 선박 ID와 연결됨. 지원하지 않는 형식은 사유와 함께 거절됨

관련: NFR-16 올린 파일 내용은 지시가 아니라 데이터로만 다룬다

### FR-03 C/P 필드 추출

- 우선순위: Must · 시작: 시스템 (계산 중 자동) · LLM · 유스케이스: UC-15
- LLM이 C/P에서 계약 조건을 정해진 스키마로 뽑는다.

입력

- C/P 문서 (FR-02)

처리

1. 문서 내용을 LLM에 보낸다 (허용 목록 안에서, NFR-15)
2. LLM이 스키마대로 값을 돌려준다 — Laytime, 일 체선료, Laycan, 계약 유형, Daylight 조항, 기상 공제 조항, Laytime 계산 단위(SHINC · Running hours)
3. 스키마 형식을 검사한다
4. 추출에 쓴 모델·프롬프트 버전을 기록한다 (NFR-03)

- 멈춤: LLM 무응답 · 1회 비용 상한 초과 → 값을 '미추출'로 두고 직접 입력한다 [가정] (NFR-11·13)
- 다른 길: 문서 안에 지시문이 있어도 데이터로만 다룬다 (NFR-16)

출력

- C/P 추출값
- → 근거 표시 FR-05 → 확인 FR-06

완료 기준: 스키마 형식 검사 100% 통과. 목업 C/P 전체에서 필드 정확도 95% 이상

관련: NFR-01 LLM은 필드 추출과 문장 작성에만 쓴다

### FR-04 NOR 필드 추출

- 우선순위: Must · 시작: 시스템 (계산 중 자동) · LLM · 유스케이스: UC-15
- LLM이 NOR에서 도착 통지 정보를 뽑아 ETANR 계산에 넘긴다.

입력

- NOR 문서 (FR-02)

처리

1. 문서 내용을 LLM에 보낸다
2. LLM이 선박명, 항차, NOR Tender 시각, 도착 장소를 돌려준다
3. NOR Tender 시각을 ETANR 계산에 넘긴다

- 다른 길: NOR이 없는 선박 → ETA로 계산한다

출력

- NOR 추출값
- → 확인 FR-06 → 정박개시의 ETANR FR-31·32

완료 기준: 추출한 NOR Tender 시각이 정박개시 산정(FR-31·FR-32)에 쓰임. NOR이 없는 선박은 ETA로 계산됨

관련: ETANR = NOR Tender, 없으면 ETA

### FR-05 추출 근거 표시

- 우선순위: Must · 시작: 시스템 (계산 중 자동) · 유스케이스: UC-15
- 추출값마다 원문 문장과 쪽 위치를 같이 보여 준다.

입력

- 추출값 (FR-03·04·11)
- 원문 문서

처리

1. 값마다 근거가 된 원문 문장과 쪽 위치를 찾는다
2. 값 옆에 근거를 표시한다

- 멈춤: 근거를 찾지 못한 값 → '미추출'로 두고 임의로 채우지 않는다

출력

- 추출값 + 근거 위치(원문 문장, 쪽)

완료 기준: 추출값 전부에 근거 위치가 있음. 근거가 없는 값은 '미추출'로 두고 임의로 채우지 않음

### FR-07 C/P–NOR 교차 검증

- 우선순위: Should · 시작: 시스템 (계산 중 자동) · 유스케이스: UC-04
- C/P, NOR, 입력값이 서로 어긋나는 곳을 찾아 표시한다.

입력

- C/P 추출값, NOR 추출값
- 입력 시나리오의 ETA · 접안 시각

처리

1. 선박명 · 항차가 같은지 본다
2. NOR Tender가 Laycan 안인지 본다
3. NOR이 ETA보다 이르거나 접안보다 늦지 않은지 본다
4. 어긋난 항목을 표시한다

출력

- 충돌 목록 (어느 항목이 어떻게 다른지)
- → 확인 FR-06

완료 기준: 충돌을 심어 둔 시험 5건이 모두 탐지됨

### FR-06 추출값 확인·수정

- 우선순위: Must · 시작: 선박 스케줄러 · 유스케이스: UC-04
- 사람이 확인한 추출값만 계산에 넣는다.

입력

- 추출값 + 근거 (FR-05)
- 충돌 표시 (FR-07), 신뢰도

처리

1. 신뢰도가 낮거나 근거와 어긋나는 값에 '확인 필요'를 붙인다
2. 스케줄러가 값을 확인하거나 고친다
3. 수정 전·후 값을 이력으로 남긴다
4. 확인된 값만 계산용 계약 조건으로 넘긴다 → FR-01

- 멈춤: 미확인 값이 남았다 → 계산을 시작하지 않는다

출력

- 확인된 계약 조건 · NOR Tender
- 수정 이력

완료 기준: 미확인 값이 있으면 계산을 시작하지 않음. 수정 전·후 값이 이력으로 남음

### FR-01 시나리오 입력

- 우선순위: Must · 시작: 선박 스케줄러 · 유스케이스: UC-05
- 계산에 넣을 선박·계약·부두·재고·접안 제한을 불러오거나 화면에서 입력·수정한다.

입력

- 템플릿 파일 (CSV · XLSX) 또는 화면 입력
- 선박 — ETA, 제원, 화물·물량, 작업시간, 입출 구분, 상태
- 계약 — Laytime, 일 체선료, Laycan, 계약 유형
- 부두, 재고, 접안 제한 정보

처리

1. 템플릿 파일을 불러온다 (또는 화면에서 직접 입력한다)
2. 불러온 값을 화면에 보여 준다
3. C/P 계약 조건과 NOR Tender는 확인된 추출값(FR-06)이나 직접 입력값을 쓴다
4. ETA, 선박 상태, 작업 중 선박의 실제 시각은 입력 시나리오 값을 쓴다
5. 스케줄러가 값을 고치고 저장한다

출력

- 저장된 입력 시나리오
- → 입력 검증 FR-08 → 계산

완료 기준: 울산 CLX 데모 시나리오 4종(평상시, 강풍 예보, 선박 집중, 부두 정비)을 오류 없이 불러옴. 화면에서 고친 값이 다음 계산에 반영됨

관련: FIX 선박의 부두·ETB(FR-17), 부두 사용 제한 구간(FR-22), 조석 시간창(FR-24), 출하 마감(FR-25)도 여기서 넣는다

### FR-08 입력 검증

- 우선순위: Must · 시작: 시스템 (계산 중 자동) · 유스케이스: UC-06
- 계산 전에 입력 오류를 찾고, 오류가 있으면 계산을 시작하지 않는다.

입력

- 입력 시나리오 (FR-01)
- 기준 정보 (FR-09)

처리

1. 필수값 누락을 검사한다
2. 형식 오류를 검사한다
3. 시각 순서 · 값 범위 오류를 검사한다
4. ID 중복 · 미등록 참조를 검사한다
5. 오류가 없으면 계산으로 넘긴다

- 멈춤: 오류가 있다 → 계산을 시작하지 않고 선박·항목·사유를 표시한다

출력

- 검증 통과 → 계산 시작
- 또는 오류 목록 (선박 · 항목 · 사유)

완료 기준: 오류 시험 10건이 모두 계산 전에 걸리고 선박·항목·사유가 표시됨

## G3 제약 판정 · ETB 산정

- 단계: 계산 · 누가: 시스템 (규칙 엔진) · 유스케이스: UC-06 · 17
- 배정안 하나를 놓고, 선박이 그 부두에 언제 댈 수 있는지(ETB)와 그 배정이 가능한지를 정한다.
- 다음으로 넘기는 것: 선박별 ETB · 제약 판정 결과

흐름

- **배정안 하나를 판정하는 순서**
  - 1. [시스템] 들어갈 수 없는 부두 빼기 (FR-14 · FR-15)
    - 멈춤: 매핑표에 없는 자재코드 → 입력 오류
  - 2. [시스템] 움직이지 않을 선박 정하기 (FR-17 · FR-18)
  - 3. [시스템] 제약마다 접안 가능시각 구하기 (FR-16·19·20·21·22·24)
  - 4. [시스템] ETB = 가장 늦은 시각 (FR-27)
  - 5. [시스템] ETU 다시 구하고 전체 재검사 (FR-27 → FR-29)
  - 6. [시스템] 안 되는 배정 걸러 내기 (FR-17 · FR-23 · FR-25)
    - 멈춤: FIX 침범 · 재고 초과/부족 · 마감 초과 → 그 배정은 불가
  - → ETB와 판정이 체선료 계산으로 (G4)
- **사람이 조건을 바꿀 때 (선택)**
  - 1. [선박 스케줄러] 임시 조건 추가 (FR-26)
  - 2. [선박 스케줄러] 제약 켜고 끄기 (FR-28)
  - 3. [시스템] 후보 다시 계산 (FR-42)
    - 멈춤: 후보 없음 → '실행 가능한 후보 없음'
  - → '추가 조건' · '미적용'으로 기록 (FR-26 · FR-28)

### FR-14 부두 제원 적합성

- 우선순위: Must · 시작: 시스템 (계산 중 자동) · 유스케이스: UC-06
- 선박 제원이 부두 허용 제원에 맞지 않으면 그 부두를 배정 대상에서 뺀다.

입력

- 선박 DWT · LOA · PBL · Draft, 입출 구분 (FR-01)
- 부두 허용 제원 (FR-09)

처리

1. 최대 DWT, 최대·최소 LOA, 최소 PBL, 최대 Draft 5종을 비교한다
2. Draft는 수입선만 비교한다
3. 맞지 않는 부두를 그 선박의 배정 대상에서 뺀다

출력

- 선박별 배정 가능 부두 목록
- 제외한 부두와 사유

완료 기준: 항목 5종(최대 DWT, 최대·최소 LOA, 최소 PBL, 최대 Draft)별 위반 시험에서 해당 부두가 제외되고 사유가 표시됨

### FR-15 화물 그룹 적합성

- 우선순위: Must · 시작: 시스템 (계산 중 자동) · 유스케이스: UC-06
- 자재코드를 화물 그룹으로 분류하고, 그 그룹을 취급하지 않는 부두를 뺀다.

입력

- 선박의 자재코드 (FR-01)
- 자재코드 → 화물 그룹 매핑표, 부두별 취급 화물 그룹 (FR-09)

처리

1. 자재코드를 화물 그룹으로 분류한다
2. 그 그룹을 취급하지 않는 부두를 배정 대상에서 뺀다

- 멈춤: 매핑표에 없는 자재코드 → 입력 오류로 표시한다

출력

- 선박의 화물 그룹
- 배정 가능 부두 목록

완료 기준: 시험 자재코드 10개가 정답 그룹으로 분류됨. 매핑표에 없는 자재코드는 입력 오류로 표시됨

### FR-17 FIX 선박 보호

- 우선순위: Must · 시작: 시스템 (계산 중 자동) · 유스케이스: UC-06
- FIX 선박의 부두·ETB를 모든 후보에서 그대로 둔다.

입력

- FIX 선박의 부두 · ETB (입력값)
- 선행 일반 선박의 ETU, Switching 시간

처리

1. FIX 선박의 부두·ETB를 입력값으로 고정한다
2. 선행 일반 선박의 ETU + Switching ≥ FIX 선박 ETB → 그 배정을 불가로 판정한다

- 멈춤: 일반 선박이 FIX 선박 시각을 침범 → 그 배정은 후보가 될 수 없다

출력

- 고정된 FIX 일정
- 불가 판정

완료 기준: 모든 후보에서 FIX 선박의 부두·ETB가 입력값과 같음. 같은 시각 경계 시험이 정답과 일치함

### FR-18 선박 상태 반영

- 우선순위: Should · 시작: 시스템 (계산 중 자동) · 유스케이스: UC-06
- 선박 상태에 따라 다시 배정할 선박과 그대로 둘 선박을 나눈다.

입력

- 선박 상태 — ORDERED, PLANNED, WORKING, COMPLETED (FR-01)

처리

1. ORDERED · PLANNED → 재배정 대상으로 둔다
2. WORKING → 옮기지 않고 현재 부두 점유로 반영한다
3. COMPLETED → 바꾸지 않는다

출력

- 재배정 대상 선박 목록
- 점유 중인 부두와 시각

완료 기준: WORKING·COMPLETED 선박의 부두·시각이 모든 후보에서 바뀌지 않음

### FR-16 선행 선박 반영

- 우선순위: Must · 시작: 시스템 (계산 중 자동) · 유스케이스: UC-06
- 같은 부두의 앞 선박을 보고 접안 가능시각을 정한다.

입력

- ETA (FR-01)
- 부두별 Direction · Switching 시간 (FR-09)
- 선행 선박의 ETU (FR-29)

처리

1. 그 부두의 선행 선박을 판별한다
2. 접안 가능시각 = max(ETA + Direction, 선행 선박 ETU + Switching)
3. 접안 순서가 바뀌면 선행 선박을 다시 판별한다

- 다른 길: 빈 부두(선행 선박 없음) → ETA + Direction

출력

- 접안 가능시각 (선행 선박 기준)
- → ETB 통합 산정 FR-27

완료 기준: 빈 부두, 선행 선박 있음, 순서 변경 시험이 손계산과 일치함

### FR-19 야간 도선 제한

- 우선순위: Must · 시작: 시스템 (계산 중 자동) · 유스케이스: UC-06
- 야간 도선 조건에 걸리는 선박은 ETB를 직후 08:00으로 정한다.

입력

- 선박 GRT · 수입 여부 · Draft, 도착 시각
- 야간 도선 기준 (FR-09), 일몰 시각 (FR-12)

처리

1. Last POB = 일몰 − 1.5시간 또는 − 2시간 (GRT · 수입 여부 · Draft별 기준)
2. 조건에 걸리는지 본다 — Last POB 이후 도착, 또는 02:00~08:00 접안
3. 걸리면 → ETB = 직후 08:00

- 다른 길: 대상이 아닌 선박 → 조정하지 않는다

출력

- 접안 가능시각 (야간 도선 기준)
- → ETB 통합 산정 FR-27

완료 기준: Last POB 정각, 02:00, 08:00 경계 시험이 정답과 일치함. 대상이 아닌 선박은 조정되지 않음

### FR-20 동일 화물 그룹 동시 접안 제한

- 우선순위: Must · 시작: 시스템 (계산 중 자동) · 유스케이스: UC-06
- 제한 조합 부두에 같은 화물 그룹 선박이 접안 중이면 접안을 늦춘다.

입력

- 제한 조합 {#6, #7, #8}, {#1-1, #1-2, #2-7} (FR-09)
- 화물 그룹 (FR-15), 접안 중인 선박의 ETU

처리

1. 배정 부두가 제한 조합에 속하는지 본다
2. 조합 안 부두에 같은 화물 그룹 선박이 접안 중인지 본다
3. 그렇다면 → 접안 가능시각 = 접안 중인 선박 ETU − 2시간

- 다른 길: 다른 화물 그룹이거나 조합 밖 부두 → 제한하지 않는다

출력

- 접안 가능시각 (동일 화물 그룹 기준)
- → ETB 통합 산정 FR-27

완료 기준: 같은 그룹, 다른 그룹, 조합 밖 부두 시험 3건이 정답과 일치함

### FR-21 부두 동시 접안 제한

- 우선순위: Must · 시작: 시스템 (계산 중 자동) · 유스케이스: UC-06
- #4-1 · #4-2 부두는 한쪽에 접안 중이면 다른 쪽 접안을 늦춘다.

입력

- #4-1 · #4-2에 접안 중인 선박의 ETU
- 두 선박의 GRT

처리

1. #4-1 · #4-2 가운데 한쪽에 접안 중인 선박이 있는지 본다
2. 있으면 → 접안 가능시각 = 접안 중인 선박 ETU − 2시간

- 다른 길: 두 선박 모두 GRT 3,000톤 이하 → 제한하지 않는다

출력

- 접안 가능시각 (부두 동시 접안 기준)
- → ETB 통합 산정 FR-27

완료 기준: 일반 선박 쌍, 소형선 쌍(GRT 3,000톤 경계 포함) 시험이 정답과 일치함

### FR-22 부두 사용 제한

- 우선순위: Must · 시작: 시스템 (계산 중 자동) · 유스케이스: UC-06

입력

- 제한 구간 — 시작 · 종료, 적용 부두, 사유 (FR-01에서 입력)

처리

1. 제한 구간과 겹치는 신규 접안을 금지한다
2. 접안 가능시각 = 제한 종료 + Direction

출력

- 접안 가능시각 (부두 사용 제한 기준)
- → ETB 통합 산정 FR-27

완료 기준: 제한 구간과 겹치는 신규 접안이 후보에 0건. 하역 중인 선박의 작업은 중단되지 않음

### FR-24 조석 제약

- 조석 시간창 (FR-01에서 입력)

2. 밖이면 → 접안 가능시각을 시간창 안으로 조정한다

출력

- 접안 가능시각 (조석 기준)
- → ETB 통합 산정 FR-27

완료 기준: 조석 시간창 시험 1건이 손계산과 일치함

관련: [확인 필요] 멘토링 자료 12쪽에는 만조·간조를 고려하지 않는다고 적혀 있었다

### FR-27 ETB 통합 산정

- 우선순위: Must · 시작: 시스템 (계산 중 자동) · 유스케이스: UC-06
- 제약들이 각각 낸 접안 가능시각 가운데 가장 늦은 시각을 ETB로 정한다.

입력

- 접안 가능시각 6개 — 선행 선박 FR-16, 야간 도선 FR-19, 동일 화물 그룹 FR-20, 부두 동시 접안 FR-21, 부두 사용 제한 FR-22, 조석 FR-24

처리

1. ETB = 제약별 접안 가능시각 가운데 가장 늦은 시각
2. ETB가 바뀌면 ETU를 다시 구한다 (FR-29)
3. 전체 제약을 다시 검사한다
4. 다음 FIX 선박과 충돌하는지 다시 검사한다 (FR-17)

출력

- 선박별 ETB
- 제약 판정 결과
- → 작업 시각 산정 FR-29

완료 기준: 제약 2개 이상이 겹치는 시험 5건에서 ETB와 판정이 정답과 일치함

### FR-23 재고 제약

- 우선순위: Must · 시작: 시스템 (계산 중 자동) · 유스케이스: UC-06
- 일 단위로 탱크 용량 초과와 재고 부족을 판정한다.

입력

- 재고 (FR-01)
- 선박 물량 · 입출 구분, 배정 일정

처리

1. 일 단위로 재고를 계산한다
2. 원유 입고 → 저장 용량을 넘는지 본다
3. 제품 출하 → 재고가 모자라는지 본다
4. 넘거나 모자라면 → 그 배정을 불가로 처리한다

- 멈춤: 용량 초과 · 재고 부족 → 그 배정은 후보가 될 수 없다

출력

- 불가 판정
- 날짜, 제품 그룹, 초과 · 부족량

완료 기준: 용량 초과·재고 부족 시험에서 날짜, 제품 그룹, 초과·부족량이 표시됨

### FR-25 출하 마감·우선 배정

- 우선순위: Could · 시작: 시스템 (계산 중 자동) · 유스케이스: UC-06
- 특정 선박에 접안 마감 시각이나 우선 배정을 지정하면 후보 계산에 반영한다.

입력

- 선박별 접안 마감 시각 (출하 마감)
- 우선 배정 지정 (FR-01에서 입력)

처리

1. 지정된 선박의 마감 · 우선 조건을 후보 계산에 넣는다
2. 마감을 넘기는 후보를 제외하고 사유를 표시한다

- 다른 길: 지정하지 않은 선박 → 영향이 없다

출력

- 마감 · 우선 조건이 반영된 후보
- 제외 사유

완료 기준: 마감을 넘기는 후보는 제외되고 사유가 표시됨. 지정하지 않은 선박은 영향이 없음

### FR-26 임시 조건 추가

- 우선순위: Could · 시작: 선박 스케줄러 · 유스케이스: UC-17
- 담당자가 임시 조건을 넣어 후보를 다시 계산한다.

입력

- 임시 조건 — 예: '선박 A는 B보다 먼저', '선박 C는 부두 #3 금지'

처리

1. 스케줄러가 임시 조건을 추가한다
2. 후보를 다시 계산한다 (FR-42)
3. 임시 조건을 입력 시나리오와 보고서에 '추가 조건'으로 기록한다

- 멈춤: 조건 때문에 후보가 없다 → '실행 가능한 후보 없음'을 표시한다

출력

- 다시 계산한 후보
- '추가 조건' 기록

완료 기준: 임시 조건이 시나리오와 보고서에 '추가 조건'으로 기록됨. 조건 때문에 후보가 없으면 '실행 가능한 후보 없음'이 표시됨

관련: NFR-16 입력한 글은 지시가 아니라 데이터로만 다룬다

### FR-28 제약 적용 선택

- 우선순위: Could · 시작: 선박 스케줄러 · 유스케이스: UC-17
- 제약을 하나씩 켜고 끄며 후보와 금액 변화를 본다.

입력

- 제약별 켬 · 끔 선택

처리

1. 스케줄러가 제약을 켜거나 끈다
2. 후보를 다시 계산한다

출력

- 제약별 금액 변화 표
- '미적용' 표시

완료 기준: 제약을 끈 결과는 '실행 가능'으로 표시되지 않음. 제약별 금액 변화가 표로 표시됨

## G4 체선료 계산

- 단계: 계산 · 누가: 시스템 (규칙 엔진) · 유스케이스: UC-16 · 07 · 12
- ETB가 정해진 선박 한 척의 작업 시각, 정박개시·종료, 예상 체선료를 계산한다. 계약 규칙은 테이블에서 읽는다.
- 다음으로 넘기는 것: 선박별 · 총 예상 체선료와 단계별 계산값

흐름

- **선박 한 척을 계산하는 순서**
  - 1. [시스템] 작업 시각 구하기 (FR-29)
    - 다른 길: 작업시간 없음 → 과거 실적으로 추정 FR-30
    - 멈춤: 실적도 없음 → 입력 오류
  - 2. [시스템] 정박개시 정하기 (FR-31 · FR-32)
    - 다른 길: 원유선·제품선 → Daylight 규칙 FR-32
  - 3. [시스템] 정박종료 = 정박개시 + Laytime (FR-33)
    - 다른 길: CFR Plus 원유선 → Laytime 1/2, '미확정 규칙' FR-34
  - 4. [시스템] 기상 공제 구하기 (FR-35)
  - 5. [시스템] 선박별 체선료 (FR-36)
    - 다른 길: 조기 완료 → 0
  - 6. [시스템] USD 합계 (FR-37)
    - 다른 길: 미계산·다른 통화 → '불완전'
  - → 후보 정렬과 비교 화면으로 (G5 · G6)
- **따로 쓰는 계산**
  - 1. [선박 스케줄러] 한 척만 넣어 계산 (FR-38)
  - 2. [시스템] 체선 시간을 사유별로 나누기 (FR-39)
  - 3. [시스템] 해석이 갈리는 규칙은 두 가지로 계산 (FR-40)
  - → 산출 근거 화면에 표시 (FR-46)

### FR-29 작업 시각 산정

- 우선순위: Must · 시작: 시스템 (계산 중 자동) · 유스케이스: UC-16
- ETB에서 작업시작 · 작업완료 · 호스분리 · ETU를 구한다.

입력

- ETB (FR-27)
- 작업시작 입력값(있으면), 작업시간, 호스분리 소요시간

처리

1. 작업시작 = 입력값 (없으면 ETB + 1시간)
2. 작업완료 = 작업시작 + 작업시간
3. 호스분리 = 작업완료 + 호스분리 소요시간
4. ETU = 작업완료 + 2시간

- 다른 길: 작업시간 · 호스분리 소요시간이 입력되지 않았다 → FR-30으로 추정한다

출력

- 작업시작, 작업완료, 호스분리, ETU
- → 호스분리는 체선료 FR-36, ETU는 다음 선박의 선행 선박 FR-16

완료 기준: 정답 사례의 4개 시각이 모두 일치함. 입력 없는 선박의 작업시작 = ETB + 1시간

### FR-30 작업시간 추정

- 우선순위: Should · 시작: 시스템 (계산 중 자동) · 유스케이스: UC-16
- 작업시간·호스분리 소요시간이 없으면 과거 실적으로 추정한다.

입력

- 과거 실적 (FR-10)
- 선박코드 · 자재코드 · 부두, 물량

처리

1. 1차 — 선박코드 · 자재코드 · 부두가 같은 실적을 찾는다
2. 없으면 2차 — 자재코드 · 부두가 같은 실적을 찾는다
3. 평균 작업 Rate로 작업시간을, 최빈값으로 호스분리 소요시간을 추정한다
4. 근거에 매칭 단계와 실적 건수를 표시한다

- 멈춤: 1차 · 2차 모두 실적이 없다 → 입력 오류로 처리한다

출력

- 추정한 작업시간 · 호스분리 소요시간
- 매칭 단계, 실적 건수
- → 작업 시각 산정 FR-29

완료 기준: 1차 매칭, 2차 매칭, 실적 없음 시험이 기대값과 일치함. 근거에 매칭 단계와 실적 건수가 표시됨

### FR-31 정박개시 산정(Daylight 미적용)

- 우선순위: Must · 시작: 시스템 (계산 중 자동) · 유스케이스: UC-16
- ETANR, Laycan, ETB로 Laytime이 시작되는 시각을 정한다.

입력

- ETANR = NOR Tender (없으면 ETA)
- Laycan From · To
- ETB (FR-27)

처리

1. ETANR · ETB가 모두 Laycan From 이전 → 정박개시 = ETB
2. ETANR이 Laycan To 이후 → 정박개시 = ETB
3. ETANR이 Laycan From 이전 → 정박개시 = Laycan From 당일 06:00
4. 그 외 → ETANR + 6시간과 ETB 가운데 이른 시각

출력

- 정박개시
- → Laytime 적용 FR-33

완료 기준: 4개 분기와 경계값(ETANR = Laycan From, ETANR = Laycan To) 시험이 정답과 일치함

관련: 위에서부터 차례로 따져 처음 맞는 줄을 쓴다

### FR-32 정박개시 산정(Daylight 적용)

- 우선순위: Must · 시작: 시스템 (계산 중 자동) · 유스케이스: UC-16
- 원유선·제품선은 일출·일몰을 따져 정박개시를 정한다.

입력

- ETANR, 선종
- 일출 · 일몰 시각 (FR-12)
- ETB (FR-27)

처리

1. ETANR이 일출~일몰 사이 → ETANR + 6시간
2. ETANR이 일출 전 → 당일 07:00
3. ETANR이 일몰 후 → 다음 날 07:00
4. 위 결과보다 ETB가 더 이르면 → 정박개시 = ETB

출력

- 정박개시
- → Laytime 적용 FR-33

완료 기준: 선종별 적용 여부와 일출·일몰 경계 시험이 정답과 일치함

관련: Daylight 적용 선종(원유선·제품선)은 기준 정보 FR-09에서 읽는다

### FR-33 Laytime 적용

- 우선순위: Must · 시작: 시스템 (계산 중 자동) · 유스케이스: UC-16
- 계약 유형별 Laytime을 더해 정박종료를 구한다.

입력

- 정박개시 (FR-31·32)
- 계약 유형, Laytime (FR-01·06)

처리

1. 계약 유형에 맞는 Laytime 규칙을 고른다
2. 정박종료 = 정박개시 + Laytime
3. 적용한 규칙 이름을 남긴다

출력

- 정박종료
- 적용 규칙 이름
- → 체선료 FR-36

완료 기준: 계약 유형이 다른 선박에서 정박종료와 적용 규칙 이름이 정답과 일치함

관련: NFR-05 규칙은 코드가 아니라 테이블에서 읽는다 · NFR-06 규칙 ID

### FR-34 CFR Plus 특례

- 우선순위: Could · 시작: 시스템 (계산 중 자동) · 유스케이스: UC-16
- CFR Plus 계약 원유선의 Laytime 1/2 조정을 별도 규칙으로 적용한다.

입력

- 계약 유형 = CFR Plus, 선종 = 원유선
- Laytime

처리

1. CFR Plus 계약 원유선인지 본다
2. Laytime 1/2 조정 규칙을 적용한다
3. 규칙이 확정되기 전에는 결과에 '미확정 규칙'을 표시한다

출력

- 조정된 Laytime
- '미확정 규칙' 표시

완료 기준: 규칙 확정 전 결과에는 '미확정 규칙'이 표시됨

관련: NFR-08 미확정 규칙이 든 결과는 '확정'으로 표시하지 않는다

### FR-35 기상 공제

- 우선순위: Must · 시작: 시스템 (계산 중 자동) · 유스케이스: UC-16
- 기상 악화로 생긴 체선 시간의 절반을 뺀다.

입력

- 기상 악화로 인한 체선 시간
- 공제 전 체선 시간

처리

1. 기상 공제 = 기상 악화로 인한 체선 시간 × 1/2
2. 체선 시간에서 기상 공제를 뺀다
3. 결과가 0 미만이면 → 0으로 한다
4. 공제 전·후 체선 시간을 근거에 남긴다

출력

- 기상 공제 시간
- 공제 전 · 후 체선 시간
- → 체선료 FR-36

완료 기준: 공제 전·후 체선 시간이 근거에 표시되고 정답과 일치함

관련: [확인 필요] '기상 악화로 인한 체선 시간'을 어떻게 재는지 요구사항서에 없다

### FR-36 선박별 예상 체선료

- 우선순위: Must · 시작: 시스템 (계산 중 자동) · 유스케이스: UC-16
- 선박 한 척의 예상 체선료를 계산한다.

입력

- 호스분리 (FR-29)
- 정박종료 (FR-33)
- 기상 공제 (FR-35)
- 일 체선료 (FR-01·06)

처리

1. 체선 시간 = max(0, 호스분리 − 정박종료 − 기상 공제)
2. 체선료 = 체선 시간 × 일 체선료 ÷ 24

- 다른 길: 조기 완료(호스분리가 정박종료보다 이르다) → 0으로 표시한다

출력

- 선박별 체선 시간 · 예상 체선료
- → 합계 FR-37, 비교표 FR-45, 산출 근거 FR-46

완료 기준: 정답 세트 전 사례 일치율 100%. 조기 완료 선박은 0으로 표시됨

관련: NFR-01 금액 계산에 LLM 호출 0건 · NFR-07 KST·분 단위, USD 센트 단위 정수

### FR-37 시나리오 합계

- 우선순위: Must · 시작: 시스템 (계산 중 자동) · 유스케이스: UC-16
- 선박별 예상 체선료를 USD로 합산한다.

입력

- 선박별 예상 체선료 (FR-36)

처리

1. 선박별 금액을 USD로 합산한다
2. 미계산 선박이나 다른 통화가 있는지 본다

- 다른 길: 미계산 선박 · 다른 통화가 있다 → 합계를 '불완전'으로 표시한다

출력

- 총 예상 체선료
- → 후보 정렬 FR-42, 비교표 FR-45

완료 기준: 합계와 선박별 금액 합의 차이 0

### FR-38 단일 선박 체선료 계산

- 우선순위: Should · 시작: 선박 스케줄러 · 유스케이스: UC-07
- 선박 한 척의 시각·계약만 넣어 최적화 없이 체선료를 계산한다.

입력

- 선박 한 척의 시각
- 계약 조건

처리

1. 스케줄러가 한 척의 시각과 계약을 입력한다
2. FR-29 → FR-36 순서로 계산한다 (최적화는 하지 않는다)
3. 예상 체선료와 단계별 계산값을 보여 준다

- 멈춤: 필수값이 빠졌다 → 계산하지 않고 빠진 항목을 알려 준다 [가정]

출력

- 예상 체선료
- 단계별 계산값

완료 기준: 정답 세트의 한 척 사례가 모두 일치함

### FR-39 체선 사유 분해

- 우선순위: Should · 시작: 시스템 (계산 중 자동) · 유스케이스: UC-12
- 체선 시간을 사유별 시간과 금액으로 나눈다.

입력

- 선박별 체선 시간 (FR-36)
- 대기 구간과 그 사유 (제약 판정 결과)

처리

1. 체선 시간을 사유별로 나눈다 — 접안 전 대기, 선행 선박 대기, 야간 도선, 부두 제한, 재고·설비, 미상
2. 사유별 시간과 금액을 표시한다

- 다른 길: 사유를 알 수 없는 구간 → '미상'으로 표시한다

출력

- 사유별 시간 · 금액
- → 산출 근거 화면 FR-46

완료 기준: 사유별 시간의 합이 체선 시간과 같음(차이 0). 사유를 알 수 없는 구간은 '미상'으로 표시됨

### FR-40 규칙 해석 대안 계산

- 우선순위: Could · 시작: 시스템 (계산 중 자동) · 유스케이스: UC-12
- 해석이 갈리는 규칙은 기본 계산과 대안 계산을 같이 보여 준다.

입력

- 대상 규칙 목록 — NOR 기준 시각, CFR Plus 공제 순서

처리

1. 해당 규칙이 걸린 선박을 찾는다
2. 기본 해석과 대안 해석으로 각각 계산한다
3. 두 금액과 차이를 표시한다

출력

- 기본 금액, 대안 금액, 차이
- → 산출 근거 화면 FR-46

완료 기준: 대상 규칙 목록이 있고, 해당 선박에 두 금액과 차이가 표시됨

## G5 기준안 · 후보 생성

- 단계: 계산 · 누가: 선박 스케줄러가 실행 · 시스템 (최적화) · 유스케이스: UC-06
- 도착순 기준안을 만들고, 제약을 모두 지키면서 총 예상 체선료가 낮은 후보를 최대 3개 찾는다.
- 다음으로 넘기는 것: 기준안 + 후보 최대 3개 · 실행 기록

흐름

- **계산 한 번**
  - 1. [선박 스케줄러] 계산 실행 (FR-42)
  - 2. [시스템] 입력 검증 (FR-08)
    - 멈춤: 오류 → 시작 안 함
  - 3. [시스템] 기준안 만들기 (도착순) (FR-41)
  - 4. [시스템] 배정안 탐색 — 배정안마다 G3 → G4 (FR-42)
    - 다른 길: 제한시간 초과 → 최선안 + 최적성 갭
    - 멈춤: 계산 오류 → 입력 보존, 원인 표시
  - 5. [시스템] 총액 낮은 순 최대 3개 (FR-42)
    - 멈춤: 가능한 배정 없음 → FR-43
    - 다른 길: 나은 후보 없음 → '개선 없음'

### FR-41 기준안(FCFS) 산정

- 우선순위: Must · 시작: 시스템 (계산 중 자동) · 유스케이스: UC-06
- 도착순으로 배정한 비교용 기준안을 후보와 같은 규칙으로 계산한다.

입력

- 검증을 통과한 입력 시나리오 (FR-08)
- 배정 가능 부두 (FR-14·15)

처리

1. 선박을 ETA 순서로 놓는다
2. 각 선박을 접안 가능시각이 가장 이른 부두에 배정한다
3. 후보와 같은 규칙으로 ETB와 체선료를 계산한다 (FR-16~37)
4. '비교용 기준안(현행 실적 아님)'이라고 표시한다

출력

- 기준안 — 부두 배정, 선박별 · 총 예상 체선료
- → 비교 FR-44·45

완료 기준: 모든 시나리오에 기준안이 생성되고 '비교용 기준안(현행 실적 아님)'으로 표시됨

관련: NFR-12 계산 중 오류가 나도 기준안은 계속 제공한다

### FR-42 후보 생성

- 우선순위: Must · 시작: 선박 스케줄러 · 유스케이스: UC-06
- 제약을 모두 지키면서 총 예상 체선료가 낮은 접안 순서·부두 배정 후보를 최대 3개 만든다.

입력

- 검증을 통과한 입력 시나리오 (FR-08)
- 배정 가능 부두 (FR-14·15)
- 기준안 (FR-41)

처리

1. 스케줄러가 계산을 실행한다
2. 접안 순서와 부두 배정을 바꿔 가며 탐색한다
3. 배정안마다 ETB를 구하고 (FR-16~27) 체선료를 계산한다 (FR-29~37)
4. 제약을 모두 지키는 배정안 가운데 총 예상 체선료가 낮은 순으로 최대 3개를 고른다
5. 후보끼리는 1척 이상 배정이 다르게 한다

- 다른 길: 기준안보다 나은 후보가 없다 → '개선 없음'으로 표시한다
- 다른 길: 최적성을 증명하지 못한 후보 → '최선 탐색 결과'로 표시한다
- 다른 길: 탐색 제한시간을 넘겼다 → 그때까지의 최선안과 최적성 갭을 표시한다 (NFR-09)
- 멈춤: 실행 가능한 배정이 없다 → FR-43
- 멈춤: 계산 중 오류 → 입력값을 보존하고 원인(선박, 제약, 모듈)을 표시한다 (NFR-12)

출력

- 후보 최대 3개 — 순서, 부두, ETB, 선박별 · 총 체선료
- 실행 기록 (입력 · 규칙 · 엔진 · 솔버 설정)

완료 기준: 검증 시나리오 전체에서 후보의 제약 위반 0건. 개선이 없으면 '개선 없음', 최적성 미증명 후보는 '최선 탐색 결과'로 표시됨

관련: NFR-01 후보 정렬에 LLM 0건 · NFR-02 10회 실행해 같은 결과 · NFR-09 8척 30초 · NFR-10 12척 60초 · NFR-18 실행 로그

### FR-43 후보 없음 처리

- 우선순위: Should · 시작: 시스템 (계산 중 자동) · 유스케이스: UC-06
- 제약을 모두 지키는 배정이 없으면 그 사실과 이유를 보여 준다.

입력

- 탐색 결과
- 배정안별 위반 내역

처리

1. 실행 가능한 배정이 없는지 확인한다
2. '실행 가능한 후보 없음'을 표시한다
3. 주요 위반 제약 · 선박 · 부두 · 시각을 표시한다

- 멈춤: 위반한 배정을 정상 후보처럼 표시하지 않는다

출력

- '실행 가능한 후보 없음'
- 주요 위반 제약 · 선박 · 부두 · 시각

완료 기준: 후보가 없는 시험에서 위반 후보가 정상 후보로 표시되지 않음

관련: NFR-08 결과 상태 '후보 없음'

## G6 비교 · 근거 조회

- 단계: 후보 비교 · 누가: 선박 스케줄러 · 체선 지불 부서 · 유스케이스: UC-08 · 12
- 기준안과 후보를 금액과 일정으로 나란히 보고, 선박 한 척의 금액이 어떻게 나왔는지 끝까지 따라가 본다.
- 다음으로 넘기는 것: 비교표 · 타임라인 · 선박별 산출 근거

흐름

- **비교 화면**
  - 1. [선박 스케줄러] 비교 화면 열기 (FR-45)
  - 2. [시스템] 후보 비교표 (FR-45)
    - 다른 길: 후보 없음 → 기준안만
  - 3. [시스템] 부두별 타임라인 (FR-44)
  - 4. [선박 스케줄러] 선박 고르기 (FR-46)
  - 5. [시스템] 산출 근거 표시 (FR-46 · 39 · 40)

### FR-45 후보 비교표

- 우선순위: Must · 시작: 선박 스케줄러 · 유스케이스: UC-08
- 후보별 금액과 기준안 대비 차이를 표로 보여 준다.

입력

- 기준안 · 후보의 선박별 · 총 예상 체선료 (FR-36·37)

처리

1. 후보별 총 예상 체선료를 표시한다
2. 기준안 대비 절감액을 계산한다
3. 변경 선박 수를 센다
4. 선박별 체선료 증감을 표시한다

- 다른 길: 후보가 없다 → 기준안과 '실행 가능한 후보 없음'만 보여 준다 (FR-43)

출력

- 후보 비교표
- → 보고서 FR-51

완료 기준: 후보 총액 = 선박별 금액 합, 선박별 증감 합 = 절감액(차이 0)

관련: NFR-08 결과마다 상태와 '가상 데이터' · '의사결정 보조용' 문구

### FR-44 부두별 타임라인

- 우선순위: Must · 시작: 선박 스케줄러 · 유스케이스: UC-08

### FR-51 후보 제안 보고서 초안

  - 4. [시스템] 결과표 만들기 (FR-58)
    - 다른 길: 불일치 → 기대값·실제값·규칙 ID
  - 5. [시스템] 6척 이하는 전수 비교 (FR-59)
    - 다른 길: 다르면 시나리오 저장

### FR-56 정답 세트 관리

- 우선순위: Must · 시작: 검증 담당자 · 유스케이스: UC-14
- 문서별 정답 필드값과 기대 체선 시간·금액을 파일로 관리한다.

입력

- 목업 C/P · NOR 문서
- 손으로 계산한 체선 시간 · 금액

처리

1. 문서별 정답 필드값을 적는다
2. 기대 체선 시간 · 금액을 적는다
3. 파일로 관리한다

출력

- 정답 세트 파일
- → 검증 일괄 실행 FR-58

완료 기준: 목업 문서 전체에 필드 정답과 금액 정답이 있음

관련: NFR-06 정답 사례가 규칙 ID를 참조한다

### FR-57 검증 시나리오

- 우선순위: Must · 시작: 검증 담당자 · 유스케이스: UC-14
- 제약마다 검증 시나리오를 만들고 통합 시나리오를 둔다.

입력

- 제약 판단 요구사항 목록 (FR-14~27)
- 시나리오별 기대 결과

처리

1. 제약 판단 요구사항마다 검증 시나리오를 1건 이상 만든다
2. 통합 시나리오(기상 악화 + 선박 집중)를 만든다
3. 시나리오마다 기대 결과를 적는다

출력

- 검증 시나리오 파일
- → 검증 일괄 실행 FR-58

완료 기준: 모든 시나리오에 기대 결과가 적혀 있음

### FR-58 검증 일괄 실행

- 우선순위: Must · 시작: 검증 담당자 · 유스케이스: UC-14
- 정답 세트와 검증 시나리오를 명령 한 번으로 돌려 결과표를 만든다.

입력

- 정답 세트 (FR-56)
- 검증 시나리오 (FR-57)

처리

1. 검증 담당자가 명령 한 번으로 실행한다
2. 결과표를 만든다 — 체선료 일치율, 제약 위반 건수, 기준안 대비 절감액, 불일치 항목
3. 필드별 파싱 정확도와 오류 유형(누락 · 오인식 · 단위 오류)을 넣는다
4. 금액 불일치 원인(파싱 오류 / 규칙 오류)을 넣는다

- 다른 길: 불일치 사례 → 기대값 · 실제값 · 관련 규칙 ID를 표시한다
- 다른 길: 금액이 틀린 사례 → 원인이 파싱인지 규칙인지 표시한다

출력

- 검증 결과표

완료 기준: 불일치 사례마다 기대값·실제값·관련 규칙 ID가 표시됨. 금액이 틀린 사례마다 원인이 파싱인지 규칙인지 표시됨

관련: NFR-20 PR마다 자동 실행, 실패하면 병합 차단 · NFR-18 실행 로그

### FR-59 최적성 검증

- 우선순위: Should · 시작: 검증 담당자 · 유스케이스: UC-14
- 작은 시나리오에서 모두 탐색한 결과와 후보 생성 결과를 비교한다.

입력

- 선박 6척 이하 입력 시나리오

처리

1. 가능한 배정을 모두 탐색한다
2. 후보 생성 결과의 총 체선료와 비교한다

- 다른 길: 두 결과가 다르다 → 해당 시나리오를 저장한다

출력

- 비교 결과 (같음 / 다름)

완료 기준: 비교 시나리오 5건에서 두 결과가 같음. 다르면 해당 시나리오가 저장됨

## 아직 정해지지 않은 것

1. **체선 지불 부서와 입출항 작업 지시자가 화면을 직접 쓰는가** (FR-46 · 확정 계획 확인) — 보고서·메일로만 받는다면 조회 화면과 역할이 달라진다.
2. **메일을 받는 사람** (FR-52) — '선박 스케줄러에 보낼 메일'의 스케줄러가 시스템을 쓰는 담당자와 같은 사람인지.
3. **기준 정보, 과거 실적, 공공데이터를 넣는 사람** (FR-09 · 10 · 12 · 13) — 요구사항서에 주체가 없어 '기준 정보 관리자'라는 역할을 두었다.
4. **공공데이터 수집이 수동인가 자동인가** (FR-13) — 받은 조석·기상 값을 계산에 바로 넣는지, 스케줄러가 보고 입력하는지도 같이 정한다.
5. **조석 제약을 그대로 둘지** (FR-24) — 멘토링 자료 12쪽에는 만조·간조를 고려하지 않는다고 적혀 있었다. 요구사항서는 Must다.
6. **기상 공제의 '기상 악화로 인한 체선 시간'을 재는 법** (FR-35) — 요구사항서와 멘토링 자료 모두 정의가 없다. 부두 사용 제한 구간과 겹친 시간으로 볼지 정해야 한다.
7. **LLM이 응답하지 않을 때 문서 추출을 어떻게 대신하는가** (FR-03 · FR-04) — NFR-11에는 초안 쪽 대체(템플릿 문장)만 분명하다.
8. **단계가 '끝났다'는 기준** (FR-60) — 다음 단계를 막는 조건을 단계마다 정해야 한다. 지금은 입력 → 계산만 분명하다.
9. **검증 단계를 누가 쓰는가** (FR-58 · FR-60) — 화면 단계의 마지막 '검증'과 '명령 한 번'이 같은 사람의 일인지.
