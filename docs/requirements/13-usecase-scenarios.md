# 유스케이스 시나리오

- 작성: 2026-11-11 · 상태: **제안 (팀 확인 전)**
- 기준: 팀 구글 문서 '[판교_2반_1조] 프로젝트정의 요구사항서'의 **실시간 탭 3절** (FR-01~60, NFR-01~22. 1.0 탭과 내용이 같다)
- 그림: [`12-usecase-diagram.md`](12-usecase-diagram.md) · 그림 파일 [`usecase/usecase-diagram.png`](usecase/usecase-diagram.png)

## 읽는 법

- 여기서 **시나리오**는 유스케이스 시나리오다. 액터와 시스템이 무엇을 어떤 순서로 주고받는지 적은 글이다. 요구사항서의 '시나리오'(FR-01, 계산에 넣는 입력 한 묶음)와 다른 말이라서, 그쪽은 **입력 시나리오**라고 적었다.
- **기본 흐름**은 아무 문제 없이 끝나는 길이다. **대안**은 다른 길로 가도 목표를 이루는 경우, **예외**는 목표를 이루지 못하고 멈추는 경우다.
- `2a`는 기본 흐름 2번에서 갈라진다는 뜻이다. `*`는 어느 단계에서나 생길 수 있다는 뜻이다.
- 괄호 안의 FR · NFR 번호가 그 문장의 근거다.
- **[가정]** 은 요구사항서에 없어서 내가 채운 것, **[확인 필요]** 는 팀이나 멘토에게 물어야 하는 것이다.

## 순서

유스케이스 다이어그램에는 순서가 없다. 순서는 FR-60(업무 단계 안내)이 정하고, 각 유스케이스의 사전조건에 적었다. FR-60은 앞 단계가 끝나지 않으면 다음 단계로 넘어가지 못하게 한다.

| FR-60의 단계 | 유스케이스 |
|---|---|
| (준비) | UC-01, UC-02, UC-03 |
| 입력 | UC-04, UC-05 |
| 계산 | UC-06 (UC-07은 따로 쓰는 계산기) |
| 후보 비교 | UC-08, UC-12 |
| 리스크 | UC-09 |
| 보고서 | UC-10 |

| 검증 | UC-14 |

데모 한 바퀴(캔버스 성공기준 ③)는 **UC-04 · 05 → UC-06 → UC-08 → UC-09 → UC-10 → UC-11** 이다.

[확인 필요] 각 단계가 '끝났다'고 보는 기준이 요구사항서에 없다. 아래 사전조건에는 내가 읽은 대로 적었다.

## 준비

### UC-01 기준 정보를 관리한다

- 액터: 기준 정보 관리자 · 우선순위: Must · 요구사항: FR-09, FR-12, NFR-05, NFR-06
- 목표: 계산이 읽을 부두 · 화물 · 규칙 기준 정보를 등록하고 버전을 붙인다.
- 사전조건: 기준 정보 파일이 있다. 부두 허용 제원, 취급 화물 그룹, 부두별 Direction · Switching 시간, 동시 접안 제한 조합, 야간 도선 기준, Daylight 적용 선종, 울산 기준 날짜별 일출 · 일몰 시각이다.

기본 흐름

1. 관리자가 기준 정보 파일을 등록한다. 값을 고쳤으면 고친 파일로 바꾼다. (FR-09, FR-12)
2. 시스템이 형식과 빠진 항목을 검사한다.
3. 시스템이 새 버전을 붙여 저장한다. (NFR-05)
4. 시스템이 등록된 내용을 보여 준다. 부두, 화물 그룹, 제한 조합, 일출 · 일몰 날짜 범위다.

대안 · 예외

- 2a. 형식이 틀리거나 항목이 빠졌다 → 저장하지 않고 어느 항목인지 알려 준다. [가정: 기준 정보 파일의 오류 처리는 요구사항서에 따로 없다]
- 4a. 일출 · 일몰 값이 없는 날짜가 있다 → 그 날짜에 걸리는 계산은 '미완료'로 표시된다고 알려 준다. (FR-12)

사후조건: 다음 계산부터 새 버전을 쓴다. 이전 실행은 이전 버전으로 다시 돌릴 수 있다. (NFR-05)

확인 방법: 울산 CLX의 제원, 화물 그룹, Direction · Switching 시간, 제한 조합이 등록되어 계산에 쓰인다. (FR-09) 테이블 값만 바꿔 결과가 바뀌는 시연이 2종 있다. (NFR-05) 규칙마다 ID가 붙어 코드와 정답 사례가 같은 ID를 가리킨다. (NFR-06)

### UC-02 공공데이터를 수집한다

- 액터: 기준 정보 관리자(시작), 공공데이터포털 API(응답) · 우선순위: Should · 요구사항: FR-13, NFR-11, NFR-14
- 목표: 울산 기준 일출 · 일몰, 조석, 기상 예보를 받아 출처와 함께 저장한다.
- 사전조건: 포털 API 키가 저장소가 아니라 환경변수나 비밀 저장소에 있다. (NFR-14)

기본 흐름

1. 관리자가 날짜 범위를 정해 수집을 시작한다.
2. 시스템이 공공데이터포털 API에 일출 · 일몰, 조석, 기상 예보를 요청한다. (FR-13)
3. 공공데이터포털 API가 값을 돌려준다.
4. 시스템이 값을 저장하고 출처와 수집 시각을 표시한다.

예외

- 3a. 포털 API가 응답하지 않는다 → 전에 저장한 값을 그대로 쓰고 '저장된 값(수집 시각)'이라고 표시한다. (NFR-11)

사후조건: 날짜별 값이 출처 · 수집 시각과 함께 저장돼 있다.

확인 방법: 울산 기준 날짜 3개의 값이 포털 조회값과 같다. (FR-13)

[확인 필요] 수집을 사람이 시작하는지, 정해진 시각에 자동으로 도는지 요구사항서에 없다. 자동이면 시작 액터는 사람이 아니라 '시간'이 된다. 받은 조석 · 기상 값을 계산에 바로 넣는지, 스케줄러가 보고 직접 입력하는지도 정해야 한다. FR-22 · FR-24는 '입력한' 값이라고만 적혀 있다.

### UC-03 과거 실적을 적재한다

- 액터: 기준 정보 관리자 · 우선순위: Should · 요구사항: FR-10 · 확장: UC-18
- 목표: 작업시간을 추정할 때 쓸 과거 작업 실적을 넣는다.
- 사전조건: 과거 작업 실적 파일이 있다. 실데이터를 받기 전에는 가상 실적을 쓴다.

기본 흐름

1. 관리자가 과거 작업 실적 파일을 불러온다. 항목은 선박코드, 자재코드, 부두, 작업 시작 · 종료, 작업량, 호스분리 시각이다. (FR-10)
2. 시스템이 형식을 검사하고 저장한다.
3. 시스템이 적재한 건수를 보여 준다.

확장: 1번에서 실적의 출처가 SOF 문서이면 UC-18이 끼어든다.

사후조건: 작업시간 · 호스분리 소요시간 추정(UC-16의 1a)에 쓸 수 있다.

확인 방법: 가상 실적 파일을 불러와 작업시간 추정에 쓴다. (FR-10)

### UC-18 SOF 실적을 추출한다 — «extend», UC-03을 확장

- 액터: 기준 정보 관리자(UC-03의 액터), LLM API · 우선순위: Could · 요구사항: FR-11, NFR-03, NFR-15
- 끼어드는 조건: 과거 실적을 정형 파일이 아니라 과거 SOF 문서로 넣을 때
- 끼어드는 곳: UC-03의 1번

흐름

1. 관리자가 과거 SOF 문서를 올린다.
2. 시스템이 LLM API로 작업 시작 · 종료, 작업량, 호스분리 시각을 추출한다. (FR-11)
3. 시스템이 정답 필드와 견준 정확도를 보여 준다.
4. 관리자가 확인한 건만 과거 실적 형식으로 적재한다. UC-03의 2번으로 이어진다.

## 입력

### UC-04 계약 문서를 등록한다

- 액터: 선박 스케줄러 · 우선순위: Must · 요구사항: FR-02, FR-06, FR-07 · 포함: UC-15
- 목표: C/P와 NOR에 적힌 계약 조건을 사람이 확인한 값으로 시스템에 넣는다.
- 사전조건: 문서를 연결할 선박 · 항차가 있다.

기본 흐름

1. 스케줄러가 선박 · 항차를 고르고 C/P와 NOR 파일(PDF · DOCX · TXT)을 올린다. (FR-02)
2. 시스템이 형식을 확인하고 문서를 그 선박에 연결한다.
3. 시스템이 문서에서 필드를 추출한다. (포함: UC-15)
4. 시스템이 C/P와 NOR을 서로 대조해 충돌을 표시한다. 선박명 · 항차가 다른 경우, NOR Tender가 Laycan 밖인 경우, NOR이 ETA보다 이르거나 접안보다 늦은 경우다. (FR-07)
5. 시스템이 추출값을 원문 문장 · 쪽 위치와 함께 보여 주고, 신뢰도가 낮거나 근거와 어긋나는 값에 '확인 필요'를 붙인다. (FR-05, FR-06)
6. 스케줄러가 값을 확인하거나 고친다.
7. 시스템이 수정 전 · 후 값을 이력으로 남긴다. 확인된 값만 계산에 쓴다. (FR-06)

대안 · 예외

- 1a. NOR이 없는 선박이다 → C/P만 올린다. 그 선박은 ETA로 계산된다. (FR-04)
- 2a. 지원하지 않는 형식이다 → 사유와 함께 거절한다. (FR-02)
- 5a. 근거를 찾지 못한 값이 있다 → '미추출'로 두고 시스템이 채우지 않는다. 스케줄러가 UC-05에서 직접 입력한다. (FR-05, FR-01)
- 7a. 미확인 값이 남았다 → 계산(UC-06)을 시작할 수 없다. (FR-06)

사후조건: 확인된 계약 조건과 NOR Tender 시각이 선박에 연결돼 있다.

확인 방법: 목업 C/P · NOR 전체가 선박 ID와 연결된다. (FR-02) 충돌을 심어 둔 시험 5건이 모두 탐지된다. (FR-07)

### UC-15 문서 필드를 추출한다 — «include», UC-04가 항상 부른다

- 액터: LLM API · 우선순위: Must · 요구사항: FR-03, FR-04, FR-05, NFR-03, NFR-13, NFR-15, NFR-16

기본 흐름

1. 시스템이 문서 내용을 LLM API에 보낸다. 보내는 항목은 허용 목록 안에서만 고른다. (NFR-15)
2. LLM API가 정해진 스키마로 값을 돌려준다. (FR-03, FR-04)
   - C/P: Laytime, 일 체선료, Laycan, 계약 유형, Daylight 조항, 기상 공제 조항, Laytime 계산 단위(SHINC · Running hours)
   - NOR: 선박명, 항차, NOR Tender 시각, 도착 장소
3. 시스템이 스키마 형식을 검사한다. (FR-03)
4. 시스템이 값마다 원문 문장과 쪽 위치를 붙인다. (FR-05)
5. 시스템이 추출에 쓴 모델 · 프롬프트 버전과 호출 수 · 토큰 · 추정 비용을 기록한다. (NFR-03, NFR-13)

대안 · 예외

- 2a. LLM API가 응답하지 않거나 1회 비용 상한을 넘었다 → 추출을 멈추고 값을 '미추출'로 둔다. 스케줄러가 직접 입력한다. [가정: NFR-11 · NFR-13은 '저장된 값과 템플릿 문장'이라고만 적혀 있어, 추출 쪽 대체 방법은 팀이 정해야 한다]
- 4a. 근거 위치를 찾지 못한 값 → '미추출'. (FR-05)
- *. 문서 안에 '이전 지시를 무시하라' 같은 문장이 있어도 지시가 아니라 데이터로만 다룬다. (NFR-16)

확인 방법: 스키마 형식 검사 100% 통과, 목업 C/P 전체에서 필드 정확도 95% 이상. (FR-03) 같은 문서를 3회 추출한 결과가 같다. (NFR-03)

### UC-05 시나리오를 입력한다

- 액터: 선박 스케줄러 · 우선순위: Must · 요구사항: FR-01 (입력 항목은 FR-17, FR-22, FR-24, FR-25에서 쓴다)
- 목표: 계산에 넣을 선박 · 계약 · 부두 · 재고 · 접안 제한을 한 묶음(입력 시나리오)으로 만든다.
- 사전조건: 기준 정보가 등록돼 있다. (UC-01)

기본 흐름

1. 스케줄러가 템플릿 파일(CSV · XLSX)을 불러온다. (FR-01)
2. 시스템이 불러온 값을 화면에 보여 준다. 선박(ETA, 제원, 화물 · 물량, 작업시간, 입출 구분, 상태), 계약(Laytime, 일 체선료, Laycan, 계약 유형), 부두, 재고, 접안 제한 정보다.
3. 시스템이 C/P · NOR에서 추출해 확인된 값이 있으면 계약 조건과 NOR Tender에 채운다. (FR-01)
4. 스케줄러가 값을 고치거나 더 넣는다. FIX 선박의 부두 · ETB(FR-17), 부두 사용 제한 구간의 시작 · 종료 · 적용 부두 · 사유(FR-22), 조석 시간창(FR-24)이 여기에 들어간다.
5. 시스템이 입력을 저장한다.

대안

- 1a. 파일 없이 화면에서 직접 입력한다. (FR-01)
- 4a. 특정 선박에 출하 마감 시각이나 우선 배정을 지정한다. (FR-25, Could)

사후조건: 저장된 값이 다음 계산에 반영된다.

확인 방법: 울산 CLX 데모 시나리오 4종(평상시, 강풍 예보, 선박 집중, 부두 정비)을 오류 없이 불러온다. 화면에서 고친 값이 다음 계산에 반영된다. (FR-01)

메모: 입력 오류 검사(FR-08)는 계산을 시작할 때 한다. UC-06의 2번이다.

## 계산

### UC-06 접안 후보를 생성한다

- 액터: 선박 스케줄러 · 우선순위: Must · 포함: UC-16 · 확장: UC-17
- 요구사항: FR-08, FR-14~25, FR-27, FR-41, FR-42, FR-43, NFR-01, NFR-02, NFR-09, NFR-10, NFR-12, NFR-18
- 목표: 도착순 기준안과, 제약을 모두 지키면서 총 예상 체선료가 낮은 접안 순서 후보를 얻는다.
- 사전조건: 입력 시나리오가 저장돼 있다. (UC-05) 추출값에 '확인 필요'가 남아 있지 않다. (UC-04, FR-06)

기본 흐름

1. 스케줄러가 계산을 실행한다.
2. 시스템이 입력을 검증한다. 필수값 누락, 형식 오류, 시각 순서 · 값 범위 오류, ID 중복 · 미등록 참조를 본다. (FR-08)
3. 시스템이 선박마다 들어갈 수 없는 부두를 뺀다. 제원(DWT · LOA · PBL · Draft, Draft는 수입선만)과 화물 그룹으로 거른다. (FR-14, FR-15)
4. 시스템이 기준안을 만든다. ETA 순서대로 접안 가능시각이 가장 이른 부두에 배정한다. (FR-41)
5. 시스템이 접안 순서와 부두 배정을 바꿔 가며 탐색한다. 배정마다 제약별 접안 가능시각 가운데 가장 늦은 시각을 ETB로 정하고(FR-27), 예상 체선료를 계산한다. (포함: UC-16)
   - 선행 선박 (FR-16) · FIX 선박 보호 (FR-17) · 선박 상태 (FR-18) · 야간 도선 (FR-19)
   - 동일 화물 그룹 동시 접안 (FR-20) · 부두 동시 접안 (FR-21) · 부두 사용 제한 (FR-22)
   - 재고 (FR-23) · 조석 (FR-24) · 출하 마감 · 우선 배정 (FR-25)
6. 시스템이 제약을 모두 지키고 총 예상 체선료가 낮은 후보를 최대 3개 고른다. 후보끼리는 1척 이상 배정이 다르다. (FR-42)
7. 시스템이 기준안과 후보를 보여 준다. 기준안에는 '비교용 기준안(현행 실적 아님)'이라고 적는다. (FR-41)

대안 · 예외

- 2a. 입력 오류가 있다 → 계산을 시작하지 않고 선박 · 항목 · 사유를 보여 준다. 스케줄러는 UC-05로 돌아가 고친다. (FR-08)
- 5a. 제약을 모두 지키는 배정이 없다 → '실행 가능한 후보 없음'과 주요 위반 제약 · 선박 · 부두 · 시각을 보여 준다. 위반한 배정을 정상 후보처럼 보여 주지 않는다. (FR-43)
- 6a. 기준안보다 나은 후보가 없다 → '개선 없음'이라고 표시한다. (FR-42)
- 6b. 탐색 제한시간을 넘겼다 → 그때까지의 최선안과 최적성 갭을 보여 주고 '최선 탐색 결과'라고 적는다. (NFR-09, FR-42)
- *. 계산 중 오류가 났다 → 입력값을 보존하고 원인(선박, 제약, 모듈)을 보여 준다. 기준안은 계속 제공한다. (NFR-12)

사후조건: 기준안과 후보(0~3개)가 저장된다. 실행 ID와 입력 · 규칙 · 엔진 · 솔버 설정이 기록된다. (NFR-02, NFR-18)

특별 요구사항: 금액 · 시각 · 제약 판정 · 후보 정렬에는 LLM을 쓰지 않는다. (NFR-01) 부두 3곳 · 선박 8척 기준 30초 안에 끝난다. (NFR-09) 선박 12척 · 부두 3곳은 60초 안에 끝난다. (NFR-10) 같은 입력이면 10번 돌려도 금액과 후보 순위가 같다. (NFR-02)

확인 방법: 검증 시나리오 전체에서 후보의 제약 위반이 0건이다. (FR-42) 오류 시험 10건이 모두 계산 전에 걸린다. (FR-08)

### UC-16 예상 체선료를 계산한다 — «include», UC-06과 UC-07이 항상 부른다

- 액터: 없음 (부른 유스케이스 안에서 돈다) · 우선순위: Must · 요구사항: FR-29~37, NFR-01, NFR-07
- 받는 것: 선박 한 척의 ETB(또는 입력한 시각)와 계약 조건

기본 흐름

1. 작업 시각을 정한다. 작업시작은 입력값(없으면 ETB + 1시간), 작업완료는 작업시작 + 작업시간, 호스분리는 작업완료 + 호스분리 소요시간, ETU는 작업완료 + 2시간이다. (FR-29)
2. 정박개시를 정한다. 기준 시각은 ETANR(NOR Tender, 없으면 ETA)이다. Daylight를 적용하지 않는 선박은 FR-31의 네 갈래를, 원유선 · 제품선은 FR-32의 일출 · 일몰 규칙을 따른다.
3. 정박종료 = 정박개시 + Laytime. Laytime은 계약 유형별로 적용한다. (FR-33)
4. 기상 공제를 구한다. 기상 악화로 생긴 체선 시간의 1/2을 뺀다. (FR-35)
5. 체선료 = max(0, 호스분리 − 정박종료 − 기상 공제) × 일 체선료 ÷ 24. (FR-36)
6. 선박별 금액을 USD로 합산한다. (FR-37)

대안 · 예외

- 1a. 작업시간이나 호스분리 소요시간이 입력되지 않았다 → 과거 실적에서 선박코드 · 자재코드 · 부두가 같은 건(없으면 자재코드 · 부두가 같은 건)의 평균 작업 Rate와 호스분리 소요시간 최빈값으로 추정한다. 둘 다 없으면 입력 오류다. (FR-30, Should)
- 3a. CFR Plus 계약 원유선이다 → Laytime 1/2 조정을 별도 규칙으로 적용한다. 규칙이 확정되기 전에는 '미확정 규칙'이라고 표시한다. (FR-34, Could)
- 5a. 호스분리가 정박종료보다 이르다 → 체선료는 0이다. (FR-36)
- 6a. 계산하지 못한 선박이나 다른 통화가 있다 → 합계를 '불완전'으로 표시한다. (FR-37)

특별 요구사항: 모든 시각은 KST · 분 단위로 계산한다. 금액은 USD 센트 단위 정수로 계산하고 표시할 때만 반올림한다. (NFR-07)

확인 방법: 정답 세트 전 사례 일치율 100%. (FR-36)

### UC-17 조건을 바꿔 재계산한다 — «extend», UC-06을 확장

- 액터: 선박 스케줄러(UC-06의 액터) · 우선순위: Could · 요구사항: FR-26, FR-28
- 끼어드는 조건: 스케줄러가 임시 조건을 넣거나 제약을 끄고 결과를 다시 보고 싶을 때
- 끼어드는 곳: UC-06의 7번 뒤

흐름

1. 스케줄러가 임시 조건을 추가한다. 예: '선박 A는 B보다 먼저', '선박 C는 부두 #3 금지'. 또는 제약을 하나씩 켜고 끈다. (FR-26, FR-28)
2. 시스템이 후보를 다시 계산한다. UC-06의 3~7번이다.
3. 시스템이 임시 조건을 입력 시나리오와 보고서에 '추가 조건'으로 기록한다. 꺼진 제약은 '미적용'으로 표시하고, 제약별 금액 변화를 표로 보여 준다.

예외

- 2a. 조건 때문에 후보가 없다 → '실행 가능한 후보 없음'을 표시한다. (FR-26)
- 3a. 제약을 끈 결과는 '실행 가능'으로 표시하지 않는다. (FR-28)

### UC-07 한 척 체선료를 계산한다

- 액터: 선박 스케줄러 · 우선순위: Should · 요구사항: FR-38 · 포함: UC-16
- 목표: 최적화 없이 선박 한 척의 예상 체선료와 계산 과정을 바로 본다.

기본 흐름

1. 스케줄러가 선박 한 척의 시각과 계약만 입력한다. (FR-38)
2. 시스템이 예상 체선료를 계산한다. 최적화는 하지 않는다. (포함: UC-16)
3. 시스템이 예상 체선료와 단계별 계산값을 보여 준다.

예외

- 1a. 필수값이 빠졌다 → 계산하지 않고 빠진 항목을 알려 준다. [가정: FR-08과 같은 규칙을 쓴다]

확인 방법: 정답 세트의 한 척 사례가 모두 일치한다. (FR-38)

[확인 필요] 이 계산기를 체선 지불 부서도 직접 쓰는지.

## 비교 · 리스크 · 보고 · 확정

### UC-08 후보를 비교한다

- 액터: 선박 스케줄러 · 우선순위: Must · 요구사항: FR-44, FR-45, NFR-08
- 목표: 기준안과 후보를 금액과 일정으로 나란히 본다.
- 사전조건: 계산이 끝나 기준안과 후보가 있다. (UC-06)

기본 흐름

1. 스케줄러가 비교 화면을 연다.
2. 시스템이 후보 비교표를 보여 준다. 후보별 총 예상 체선료, 기준안 대비 절감액, 변경 선박 수, 선박별 체선료 증감이다. (FR-45)
3. 시스템이 기준안과 후보별 부두 타임라인을 보여 준다. 부두마다 선박의 대기 · 작업 · 호스분리~이안 구간과 야간 도선 · 부두 제한 구간이 시간축에 놓인다. 구간은 색과 라벨로 구별한다. (FR-44)
4. 스케줄러가 후보를 바꿔 가며 본다.

대안

- 2a. 후보가 없다 → 기준안과 '실행 가능한 후보 없음'만 보여 준다. (FR-43)
- *. 결과마다 상태(확정 / 가정값 포함 / 미확정 규칙 포함 / 데이터 누락 / 후보 없음)와 '가상 데이터' · '의사결정 보조용' 문구를 표시한다. (NFR-08)

확인 방법: 후보 총액 = 선박별 금액 합, 선박별 증감 합 = 절감액. 차이 0. (FR-45)

### UC-12 산출 근거를 조회한다

- 액터: 선박 스케줄러, 체선 지불 부서 · 우선순위: Must · 요구사항: FR-46, FR-39, FR-40, NFR-04
- 목표: 선박 한 척의 예상 체선료가 어떻게 나왔는지 손으로 다시 셈할 수 있을 만큼 본다.
- 사전조건: 계산 결과가 있다. (UC-06 또는 UC-07)

기본 흐름

1. 사용자가 선박을 고른다.
2. 시스템이 계산에 쓴 값을 보여 준다. ETANR, 정박개시 · 종료, ETB, 작업시작 · 완료, 호스분리, 기상 공제, 일 체선료, 적용 규칙 이름, 제약 판정 결과다. (FR-46)
3. 시스템이 체선 시간을 사유별 시간과 금액으로 나눠 보여 준다. 접안 전 대기, 선행 선박 대기, 야간 도선, 부두 제한, 재고 · 설비, 미상이다. (FR-39, Should)

대안

- 3a. 해석이 갈리는 규칙(NOR 기준 시각, CFR Plus 공제 순서)이 걸린 선박이다 → 기본 계산과 대안 계산의 금액과 차이를 같이 보여 준다. (FR-40, Could)
- 3b. 사유를 알 수 없는 구간이 있다 → '미상'으로 표시한다. (FR-39)

확인 방법: 화면에 나온 값만으로 손계산하면 같은 금액이 나온다. (FR-46) 사유별 시간의 합이 체선 시간과 같다. (FR-39) 화면과 초안의 숫자를 계산 결과와 자동 대조해 불일치가 0건이다. (NFR-04)

[확인 필요] 체선 지불 부서가 화면에서 직접 보는지, 스케줄러가 보낸 보고서로 받아 보는지. 요구사항서에는 역할별 화면이나 권한이 없다. 보고서로만 받는다면 체선 지불 부서는 액터에서 빠진다.

### UC-09 남은 리스크를 점검한다

- 액터: 선박 스케줄러 · 우선순위: Must · 요구사항: FR-47, FR-48, FR-49, FR-50
- 목표: 금액이 낮은 후보라도 현장에서 문제가 될 수 있는 점을 고르기 전에 본다.
- 사전조건: 후보가 1개 이상 있다. (UC-06)

기본 흐름

1. 스케줄러가 후보를 고른다.
2. 시스템이 5개 항목(날씨 급변, 설비, 탱크, 긴급 출하, 현장 안전)을 '해당 / 해당 없음 / 판단 불가'로 보여 주고 관련 선박 · 부두 · 시각을 연결한다. (FR-47)
3. 시스템이 '해당' · '판단 불가' 항목마다 대안과 주의할 점을 보여 준다. 문구는 리스크 유형별 문구표에서 가져온다. (FR-48)
4. 시스템이 ETA가 ±6시간 바뀌거나 기상 예보가 바뀌면 후보 순위가 달라지는지 표시한다. (FR-50)
5. 스케줄러가 리스크마다 '확인함'을 표시한다. (FR-49, Could)

사후조건: 확인 상태가 저장되고 보고서에 확인 현황이 들어간다. (FR-49)

규칙: '지금 확정' 같은 단정 표현을 쓰지 않는다. (FR-48)

확인 방법: 모든 후보에 5개 항목의 점검 결과가 있다. 위험 근거가 없는 입력 시나리오에서는 '해당'이 0건이다. (FR-47)

### UC-10 보고·메일 초안을 쓴다

- 액터: 선박 스케줄러, LLM API · 우선순위: Must · 요구사항: FR-51, FR-52, FR-53, NFR-01, NFR-04, NFR-09, NFR-11, NFR-13, NFR-15
- 목표: 고른 후보로 보고서와 메일의 초안을 받는다. 보내는 일은 사람이 한다.
- 사전조건: 후보가 있고 리스크 점검을 마쳤다. (UC-06, UC-09, FR-60)

기본 흐름

1. 스케줄러가 후보를 골라 초안을 요청한다.
2. 시스템이 계산 결과에서 금액과 시각을 가져온다. 숫자는 LLM이 만들지 않는다. (NFR-01)
3. 시스템이 LLM API에 문장 작성을 요청하고 문장을 받는다. 보내는 항목은 허용 목록 안에서만 고른다. (NFR-15)
4. 시스템이 보고서 초안을 만든다. 기준안 대비 체선료 차이, 후보별 부두 · 일정, 후보 비교표 · 타임라인 이미지, 제약 검증 결과, 남은 리스크 · 대안, 추천 이유, 입력 데이터 버전이 들어간다. 맨 위에 '담당자 검토용 초안'이라고 적는다. (FR-51)
5. 시스템이 메일 초안을 만든다. 제목, 본문, 선박별 일정이 들어간다. (FR-52)
6. 시스템이 초안의 숫자를 계산 결과와 대조한다. (NFR-04)
7. 스케줄러가 초안을 고치고, 복사하거나 .docx로 내려받는다. (FR-53)

대안 · 예외

- 3a. LLM API가 응답하지 않거나 1회 비용 상한(1달러)을 넘었다 → 템플릿 문장으로 바꾸고 '템플릿 사용'이라고 표시한다. (NFR-11, NFR-13)
- 6a. 숫자가 계산 결과와 다르다 → 다른 곳을 표시하고 초안을 내보내지 않는다. [가정: NFR-04에는 '불일치 0건'이라는 기준만 있다]

사후조건: 초안이 만들어져 있다. 메일은 스케줄러가 시스템 밖에서 보낸다. 시스템에는 발송 기능이 없다. (FR-52)

확인 방법: 초안의 금액 · 시각이 계산 결과와 모두 같다. (FR-51) 메일 초안의 숫자가 보고서와 같다. (FR-52) 보고서 초안이 1분 안에 나온다. (NFR-09)

[확인 필요] FR-52에는 "선박 스케줄러에 보낼 메일"이라고 적혀 있다. 메일을 받는 사람이 누구인지, 보내는 '담당자'와 다른 사람인지 확인해야 한다. 받기만 하는 사람은 시스템을 만지지 않으므로 액터가 아니다.

### UC-11 후보를 확정한다

- 액터: 선박 스케줄러 · 우선순위: Must · 요구사항: FR-54, FR-55, FR-49, FR-53, NFR-17
- 목표: 후보 하나를 사람이 골라 확정하고, 누가 왜 골랐는지 남긴다.
- 사전조건: 후보가 있고 보고서 단계를 마쳤다. (UC-06, UC-10, FR-60)

기본 흐름

1. 스케줄러가 후보 하나를 고르고 선택 이유를 적어 확정한다. (FR-54)
2. 시스템이 후보 ID, 입력 시나리오 버전, 시각, 선택 이유를 기록한다. 기록은 고치거나 지울 수 없다. (FR-54)
3. 시스템이 그 후보의 상태를 '추천'에서 '선택됨'으로 바꿔 화면과 보고서에 표시한다. (FR-55)

대안

- 1a. 미확인 리스크가 남아 있다 → 경고를 띄운다. 확정은 막지 않는다. (FR-49)
- 3a. 스케줄러가 확정을 취소하거나 다른 후보를 다시 고른다 → 이것도 이력에 덧붙인다. (FR-54)
- 3b. 스케줄러가 확정 일정을 CSV로 내려받는다. (FR-53)
- 3c. 현업에 반영한 뒤 스케줄러가 '현업 반영 완료'를 입력한다. (FR-55)

규칙: 확정은 사람의 동작으로만 일어난다. Agent의 도구 목록에는 확정 · 규칙 변경 · 삭제가 없다. (FR-54, NFR-17)

확인 방법: '추천'에서 '선택됨'으로 바뀌는 길이 담당자 동작 하나뿐이다. (FR-55) 확정 · 삭제 · 규칙 변경을 Agent에 요청한 시험 10건이 모두 거절된다. (NFR-17)

### UC-14 검증을 일괄 실행한다

- 액터: 검증 담당자 · 우선순위: Must · 요구사항: FR-56, FR-57, FR-58, FR-59, NFR-06, NFR-20

  - 검증 시나리오: 제약 판단 요구사항마다 1건 이상, 그리고 통합 시나리오(기상 악화 + 선박 집중). 모두 기대 결과가 적혀 있다. (FR-57)

기본 흐름

2. 시스템이 정답 세트와 검증 시나리오를 모두 돌린다.
3. 시스템이 결과표를 만든다. 체선료 일치율, 제약 위반 건수, 기준안 대비 절감액, 불일치 항목, 필드별 파싱 정확도, 오류 유형(누락 · 오인식 · 단위 오류), 금액 불일치 원인(파싱 오류 / 규칙 오류)이 들어간다. (FR-58)
4. 시스템이 불일치 사례마다 기대값 · 실제값 · 관련 규칙 ID를 보여 준다. (FR-58, NFR-06)

대안

- 2a. 선박 6척 이하 입력 시나리오다 → 가능한 배정을 모두 탐색한 결과와 후보 생성 결과의 총 체선료를 비교한다. 다르면 그 시나리오를 저장한다. (FR-59, Should)
- *. 코드나 규칙이 바뀌면 PR마다 자동으로 실행되고, 실패하면 병합이 막힌다. (NFR-20) 이때 시작하는 쪽은 사람이 아니라 CI다. [가정: 그림에는 검증 담당자만 그렸다]

[확인 필요] FR-60은 화면 단계의 마지막에 '검증'을 둔다. 이 단계를 스케줄러가 보는지, 팀이 검증할 때만 쓰는지 정해야 한다.

## 팀에 확인할 것

1. **체선 지불 부서와 입출항 작업 지시자가 화면을 직접 쓰는가.** 보고서 · 메일로만 받는다면 두 액터와 UC-13은 그림에서 빠진다. (UC-12, UC-13)
2. **FR-52의 메일을 받는 사람.** "선박 스케줄러에 보낼 메일"의 스케줄러가 시스템을 쓰는 '담당자'와 같은 사람인지. (UC-10)
3. **기준 정보 · 과거 실적 · 공공데이터를 넣는 사람.** 요구사항서에 주체가 없어 '기준 정보 관리자'라는 역할을 만들었다. 스케줄러가 직접 한다면 UC-01~03의 액터를 선박 스케줄러로 바꾼다.
4. **공공데이터 수집이 수동인가 자동인가.** 자동이면 '시간' 액터를 둔다. (UC-02)
5. **검증 단계를 누가 쓰는가.** FR-60의 마지막 단계와 FR-58의 '명령 한 번'이 같은 사람의 일인지. (UC-14)
6. **LLM이 응답하지 않을 때 문서 추출을 어떻게 대신하는가.** NFR-11에는 초안 쪽 대체(템플릿 문장)만 분명하다. (UC-15)
7. **단계가 '끝났다'는 기준.** FR-60이 다음 단계를 막는 조건을 단계마다 정해야 한다.
