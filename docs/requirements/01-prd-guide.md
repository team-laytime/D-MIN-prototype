## 1. 한 문단 요약

PRD(Product Requirements Document, 제품 요구사항 문서)는 **"무엇을, 왜, 누구를 위해 만들고, 어떤 기준을 통과하면 완성으로 보는가"를 팀이 같은 말로 합의해 적은 문서**다. 어떻게 만들지(설계)가 아니라 무엇이 되어야 하는지(요구)를 적는다. 좋은 PRD는 짧고, 문장마다 검증할 수 있고, 모르는 것을 모른다고 적고, 결정이 바뀔 때마다 버전이 올라간다.

PRD는 한 번 쓰고 끝내는 문서가 아니다. 요구사항 분석 단계에서 초안을 만들고, 이해관계자 확인을 거쳐 기준선(baseline)으로 고정한 뒤, 설계·구현 단계에서는 변경 관리를 하면서 계속 기준으로 쓴다.

## 2. PRD가 답해야 하는 일곱 질문

| # | 질문 | PRD의 어디 | 우리 프로젝트의 예 |
|---|---|---|---|
| 1 | 왜 하나? | 문제·기회 | 체선 '시간'과 체선'료' 사이의 빈칸(진단 H4) |
| 2 | 누구를 위한 것인가? | 사용자·이해관계자 | 체선료 정산 담당 / 터미널 접안계획 담당 |
| 3 | 무엇을 만드나? | 기능 요구 | 레이타임 재계산, 차이 분해, 회신 초안 |
| 4 | 얼마나 잘해야 하나? | 비기능 요구·성공 기준 | 골든 케이스 100% 일치, 근거 첨부율 100% |
| 5 | 무엇을 안 하나? | 비목표 | 체선 대시보드, 선석 최적화 솔버, 자동 확정 |
| 6 | 무엇이 아직 불확실한가? | 가정·열린 질문 | 멘토 답(Q1~Q6), 계약 조건 값 |
| 7 | 무엇부터, 언제까지? | 우선순위·마일스톤 | Must/Should/Could, 게이트 G1·F |

일곱 가지 중 하나라도 답이 없으면 PRD가 아니라 아이디어 메모다. 반대로 모두 답했다면 6~8쪽 안팎이면 충분하다 [추천].

## 4. 좋은 PRD의 여덟 가지 원칙

| # | 원칙 | 어기면 | 우리 프로젝트에서는 |
|---|---|---|---|
| 1 | 무엇·왜를 쓰고, 어떻게는 쓰지 않는다 | 요구가 구현 방식에 묶여 대안이 막힌다 | "Python으로 계산"이 아니라 "계산서 줄마다 룰 ID·SOF 행이 붙는다" |
| 2 | 모든 요구는 검증할 수 있다 | "정확하게" 같은 말로 끝나 논쟁만 남는다 | 인수 기준 = 골든 케이스 TC-01~05 정답 일치 |
| 3 | 한 줄에 한 요구, 번호 하나 | 추적도 테스트도 못 한다 | CLK-01, CLM-02 … |
| 4 | 우선순위가 있다 | 전부 중요해져 일정이 무너진다 | 마감은 고정, 범위가 변수 (MoSCoW) |
| 5 | 하지 않을 일을 쓴다 | 범위가 슬금슬금 커진다 | SEAGATE와 겹치는 대시보드·솔버는 비목표 |
| 6 | 근거와 불확실성을 표시한다 | 가정이 사실처럼 퍼진다 | 근거 등급 CONFIRMED / DOC / VIRTUAL / HYPOTHESIS |
| 7 | 추적할 수 있다 | 빠진 요구, 주인 없는 작업이 생긴다 | 요구 ID ↔ 시나리오 ↔ 룰·TC ↔ 작업 ID |
| 8 | 살아 있는 문서다 | 낡은 문서가 진실 행세를 한다 | 버전 = 게이트(v0→v1→v2), 결정 로그, 변경 이력 |

## 5. 표준 구성 — 섹션별로 무엇을 쓰나

| # | 섹션 | 쓰는 것 | 흔한 실수 |
|---|---|---|---|
| 1 | 요약 | 문제·해법·범위·결정 대기를 한 장에 | 기능 나열로 시작, 왜가 없음 |
| 2 | 배경·문제 | 누가 어떤 상황에서 무엇이 불편한가, 근거 | 해법을 문제처럼 씀("AI가 없다") |
| 3 | 목표·비목표 | 3개 이내의 목표, 명시적 비목표 | 목표가 10개, 비목표 없음 |
| 4 | 사용자·이해관계자 | 역할, 하는 일, 필요한 것 | "모든 사용자" |
| 5 | 시나리오 | 대표 흐름과 예외 흐름 | 행복한 경로만 |
| 6 | 기능 요구 | ID, 한 문장, 인수 기준, 우선순위 | 모호어, 구현 지시 |
| 7 | 비기능 요구 | 성능·보안·신뢰성·추적성·사용성을 숫자로 | 누락 → 마지막에 폭발 |
| 8 | 성공 지표 | 어떻게 재는지까지 | 잴 방법이 없는 목표 |
| 9 | 가정·제약·의존성 | 사실과 구분해 나열, 확인 방법 | 가정이 본문에 섞임 |
| 10 | 위험·대응 | 가능성·영향·대응·담당 | 위험이 일반론 |
| 11 | 릴리스·마일스톤 | 단계, 게이트, 범위 동결 | 날짜만 있고 기준이 없음 |
| 12 | 열린 질문·결정 로그 | 질문, 담당, 기한, 결정과 이유 | 구두로만 결정 |
| 13 | 부록 | 용어, 근거 문서, 조사 자료 | 본문에 다 넣어 길어짐 |

## 6. 요구사항 문장 쓰는 법

### 6-1. 세 가지 형식

| 형식 | 모양 | 쓰임 |
|---|---|---|
| shall 문장 | "시스템은 … 해야 한다" | 정밀 명세. 아래 EARS로 정형화 |
| 사용자 스토리 | "<역할>로서 <기능>을 원한다. <이유> 때문이다" | 사용자 관점의 요구. INVEST(독립·협상 가능·가치 있음·추정 가능·작음·테스트 가능)로 점검 |
| 인수 기준 | Given(전제) / When(행동) / Then(결과) | 검증 가능한 완료 조건 |

### 6-2. EARS — 요구 문장을 다섯 틀로

EARS(Easy Approach to Requirements Syntax)는 키워드 몇 개로 요구 문장의 모양을 통일해 모호함을 줄이는 방법이다 [사실, 공식 안내는 `05`에 링크].

| 패턴 | 키워드 | 틀 | 우리 예 |
|---|---|---|---|
| 상시 | 없음 | 시스템은 [응답]한다 | 시스템은 계산서의 모든 줄에 룰 ID를 붙인다 |
| 이벤트 구동 | When | [트리거]가 일어나면, 시스템은 [응답]한다 | SOF 이벤트와 계약 조건이 입력되면, 시스템은 레이타임 계산서를 낸다 |
| 상태 구동 | While | [상태]인 동안, 시스템은 [응답]한다 | 확인되지 않은 필드가 입력에 있는 동안, 시스템은 결과에 "확인 필요"를 표시한다 |
| 원치 않는 상황 | If … then | [문제 상황]이면, 시스템은 [응답]한다 | 쟁점 6종이 감지되면, 시스템은 자동 판정하지 않고 두 계산을 함께 낸다 |
| 선택 기능 | Where | [기능이 있는 경우] 시스템은 [응답]한다 | 실제 SOF 양식이 확보된 경우, 시스템은 문서에서 이벤트를 추출한다 |

둘 이상의 키워드를 순서대로 이으면 복합 패턴이 된다 (예: "While … When … 시스템은 …").

### 6-3. 나쁜 문장 → 좋은 문장 (우리 도메인)

| # | 나쁜 문장 | 왜 나쁜가 | 좋은 문장 |
|---|---|---|---|
| 1 | 시스템은 체선료를 정확하게 계산한다 | '정확'의 기준이 없다 | SOF 이벤트와 계약 조건이 입력되면, 시스템은 레이타임 계산서를 낸다. 인수: TC-01~05(+01b·05b)의 체선 시간·금액이 정답과 일치 |
| 2 | 에이전트가 청구서를 빠르게 검토한다 | '빠르게'가 얼마인가 | 청구 1건(SOF 30행 이하)의 재계산·차이 분해를 10초 이내 [가정]에 낸다 |
| 3 | 쟁점은 적절히 처리한다 | '적절히'가 무엇인가 | 쟁점 6종 중 하나가 감지되면, 자동 판정하지 않고 "담당자 확인 필요"와 두 계산 결과를 함께 낸다 |
| 4 | 근거를 제공한다 | 어디까지인지 모른다 | 계산서의 모든 줄은 룰 ID와 SOF 행 번호를 갖는다 (누락 0건) |
| 5 | 사용하기 쉬워야 한다 | 잴 수 없다 | 사용법을 처음 보는 팀원이 안내 없이 시나리오 S-A1을 15분 안에 끝낸다 (5명 중 4명) [가정] |

바꿔 써야 하는 모호어: 빠르게, 쉽게, 적절히, 필요 시, 가능한 한, 충분히, 최대한, 유연하게, "등", "기타". 숫자·조건·목록 중 하나로 바꾼다.

### 6-4. 요구 한 줄 품질 점검

요구 한 줄마다 아래를 "예/아니오"로 점검한다. ISO/IEC/IEEE 29148이 좋은 요구의 속성으로 드는 항목을 풀어 쓴 것이다 [확인 필요: 표준 원문의 정확한 목록·용어와 대조 전].

| 속성 | 점검 질문 |
|---|---|
| 필요함 | 없애면 누가 곤란한가? 출처가 있는가? |
| 적절함 | 해법이 아니라 필요를 말하는가? |
| 모호하지 않음 | 두 사람이 읽고 다르게 이해할 여지가 없는가? |
| 완전함 | 조건·예외·단위가 다 적혔는가? |
| 단일함 | 한 문장에 한 요구인가? ("그리고"가 있으면 쪼갠다) |
| 실현 가능 | 기간·자원·데이터로 가능한가? |
| 검증 가능 | 시험·시연·검토로 통과/실패를 가를 수 있는가? |
| 정합함 | 다른 요구와 충돌하지 않는가? |

## 7. 우선순위·범위·변경

### 7-1. MoSCoW

| 등급 | 뜻 | 판정 질문 |
|---|---|---|
| Must | 이번 기간에 없으면 결과물이 성립하지 않는다 | 이게 없으면 데모·평가가 성립하는가? 수작업 우회가 있으면 Must가 아니다 |
| Should | 중요하지만 빠져도 성립한다 | 빠지면 가치가 크게 줄어드는가? |
| Could | 있으면 좋다. 시간이 남을 때 한다 | 빠져도 아무도 모르는가? |
| Won't (this time) | 이번엔 안 한다. 기록은 남긴다 | 다음 기회에 할 이유가 있는가? |

마감이 고정이면 범위가 변수다. Must만으로도 쓸모 있는 결과가 나와야 하고, Must가 일정의 대부분을 차지하면 우선순위를 다시 본다 [추천].

### 7-2. 범위 동결(Freeze)과 변경 요청

- 동결 전: 자유롭게 바꾸되 결정 로그에 남긴다.
- 동결 후: 변경 요청서(무엇을·왜·일정과 범위에 주는 영향·대안·승인자)를 거친다. 승인되면 반영하되, 기존 항목 하나를 Won't로 내려 총량을 유지한다 ("넣으면 뺀다").

기준선: PRD는 게이트마다 버전을 올린다. v0(초안, 결정 대기) → v1(G1, 코어 확정) → v2(F, 범위 동결). 기준선 이후의 변경은 변경 요청을 거친다.

## 9. AI Agent 제품이라서 추가로 정할 것

## 10. 흔한 실수 12가지

1. 해법으로 시작한다 ("RAG 챗봇을 만든다").
2. 사용자를 "모든 사람"으로 둔다.
3. 비목표가 없다.
4. 모호어가 많다.
5. 한 줄에 요구가 여러 개다.
6. 인수 기준이 없다.
7. 전부 Must다.
8. 가정이 사실처럼 쓰인다.
9. 예외 흐름이 없다 (행복한 경로만).
10. 비기능 요구를 마지막에 몰아 쓴다.
11. 구현을 먼저 하고 PRD를 나중에 써서 구현을 정당화한다. 이 경우 PRD가 요구가 아니라 변명이 된다. 우리 프로젝트가 정확히 이 위험에 있다: 프로토타입이 요구보다 앞서 있고 현업 확인은 0건이다.
12. 길어서 아무도 읽지 않거나, 버전이 없어 어느 것이 최신인지 모른다.

## 11. 팀에 돌리기 전 자기 점검표

- [ ] 일곱 질문(§2)에 모두 답이 있다
- [ ] 문제 문장이 해법을 포함하지 않는다
- [ ] 목표는 3개 이내이고 비목표가 4개 이상 적혀 있다
- [ ] 모든 요구에 ID, 우선순위, 인수 기준이 있다
- [ ] 모호어 목록(§6-3)에 걸리는 문장이 없다
- [ ] Must만으로 데모·평가가 성립한다
- [ ] 모든 Must가 시나리오 한 개 이상에 나온다
- [ ] 시나리오마다 예외 흐름이 한 개 이상 있다
- [ ] 성공 지표마다 "어떻게 재는지"가 적혀 있다
- [ ] 프로젝트 안에서 잴 것과 도입 뒤에 잴 것이 나뉘어 있다
- [ ] 가정이 따로 모여 있고 가정마다 확인 질문이 있다
- [ ] 근거 등급이 요구마다 붙어 있다 (CONFIRMED가 없으면 없다고 쓴다)
- [ ] 결정 대기 항목마다 담당·기한·기본값이 있다
- [ ] 위험 표에 일정·데이터·범위 위험이 들어 있다
- [ ] AI 항목(§9) 열 가지에 답이 있다
- [ ] 버전, 날짜, 작성자, 다음 버전의 조건이 적혀 있다
- [ ] 이미 만든 것 중 범위 밖인 것의 처분이 적혀 있다
- [ ] 처음 읽는 사람이 30초 안에 "무엇을 만드는지"를 말할 수 있다
