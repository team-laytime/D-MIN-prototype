## ADR-001 언어와 서비스 수

- **상황**: 팀 6명(AI/DATA 3, BE 2, Infra 1), 기간 10/30~12/17. 예전 핸드오프 문서는 'Spring Boot API + Python 에이전트' 2개 서비스를 제안했다. 최적화·데이터·LLM SDK는 파이썬이 편하다.
- **결정**: Python 3.12 하나, 프로세스 하나(FastAPI 안에 엔진을 라이브러리로).
- **버린 안**: Spring Boot(API·인증) + Python(계산) 2개 서비스.
- **결과**: 서비스 사이 직렬화·배포·장애 지점이 없어 6주 안에 끝까지 이을 수 있었다. 대신 BE가 Java에 익숙하다면 학습이 필요하다. 엔진 입출력이 JSON이라 나중에 나누기는 쉽다.
- **다시 볼 때**: 사내 표준이 Java이거나, 인증·사용자 관리가 커질 때 → 지금 이미지를 계산 서비스로 두고 Spring Boot가 앞단을 맡는다.

## ADR-002 구조 — 모듈러 모놀리스와 안쪽 계층

- **상황**: 한 달 약 100척 규모(인프라 가이드). 어려운 것은 처리량이 아니라 '숫자가 맞고 근거가 남는가'.
- **결정**: 한 저장소·한 프로세스 안에서 계층을 나눈다. `domain`·`rules`·`engine`은 표준 라이브러리만 쓰고 LLM·DB·HTTP를 모른다. 바깥(api·store·llm·web)은 교체 가능.
- **버린 안**: 마이크로서비스(계산·최적화·보고서를 각각 서비스로).
- **결과**: 계산 경로가 순수 함수에 가까워 시험이 쉽고(커버리지 88~97%), 같은 엔진이 API·CLI·CI·컨테이너에서 똑같이 돈다. 계층 규칙은 시험(LLM import 0)으로 지킨다.
- **다시 볼 때**: 다른 시스템이 엔진만 따로 불러야 할 때.

## ADR-003 규칙은 코드가 아니라 표

- **상황**: 과제 원문 6절 "규칙을 코드에 박지 말고 계약 정보에서 읽게", 멘토링 뒤 값이 계속 바뀔 것(팀 운영 방식). PPT에도 아직 모순·빈칸이 있다.
- **결정**: 값은 `data/master`·`data/rules`의 JSON 표, 규칙마다 ID(ETB-01…)와 출처·상태, 다섯 표의 내용 해시를 '규칙 버전'으로 실행마다 기록. `rules_patch`로 표 값을 바꾼 '만약' 계산도 버전이 따로 남는다.
- **버린 안**: 코드 상수 / 룰 엔진 제품(Drools 등).
- **결과**: 공제 비율·Direction만 바꿔 금액이 바뀌는 시연(GC-09), 이전 규칙으로 다시 돌리면 같은 결과(시험). 단, '식의 모양'(분기 순서 등)이 바뀌면 코드도 고쳐야 한다(09 문서에 표시).
- **다시 볼 때**: 계약마다 식 자체가 자주 달라지면 작은 규칙 DSL을 검토.

## ADR-004 최적화 — 디코더 + 분기한정 직접 구현

- **상황**: 팀은 '수리계획법(Python 무료 도구)'을 계획했다. 그런데 PPT 규칙은 절차형이다(야간 도선, Laycan 분기, 상대 ETU − 2h, 기상 공제). 후보 금액은 계산서 금액과 한 푼도 달라선 안 된다(성공기준 ①②).
- **결정**: 결정 변수는 '부두와 순서'만, 시각은 엔진(디코더)이 정한다. 탐색은 기준안 → 지역 탐색(10척 이상은 반복) → 분기한정(ETB 비감소 순서, 하한, 상태 병합). 6척 이하는 완전 탐색과 대조.
- **버린 안**: MILP/CP-SAT로 전부 다시 쓰기 / 메타휴리스틱만(최적 증명 불가).
- **결과**: 후보 금액 = 계산서 금액(같은 함수). 데모 규모는 0.2초 안에 최적 증명, 12척 18초. 16척은 하한이 약해 갭이 크다(78.9%). 수리 모델은 문서(05)로 남겨 MILP 전환 길을 열어 둠.
- **다시 볼 때**: 15척 이상이 일상이 되면 CP-SAT로 하한을 강화하고 디코더는 검증용으로 남긴다.

## ADR-005 Agent — 코드가 흐름을 정하고 LLM은 가장자리

- **상황**: 캔버스는 '나눠 맡는 멀티 Agent', 피그마는 'Agent가 tool을 불러 계산·작성, 숫자는 엔진, 문장은 LLM'. 성공기준 ①은 일치율 100%, NFR-01·02·12·16.
- **결정**: Agent = 입출력이 고정된 역할 모듈 8개. 순서는 오케스트레이터(코드)가 피그마 1~7단계 그대로. LLM은 보고서 문장과 질의응답 두 곳, 숫자는 자리표시자로만, 쓰기 도구 없음, 1회 1달러 상한, 실패 시 템플릿.
- **버린 안**: LLM 플래너가 도구를 골라 흐름을 정하는 자율 멀티 Agent(LangGraph·CrewAI 등).
- **결과**: 같은 입력 → 같은 경로·같은 숫자, 호출은 실행당 0~1회. 대신 '스스로 판단하는 Agent'의 인상은 약하다 — 발표에서는 '판단은 엔진이 증명하고, 설명은 LLM이 한다'로 말한다.
- **다시 볼 때**: 메일·PDF 같은 비정형 입력을 읽어야 할 때 그 단계만 LLM 추출 + 사람 확인으로.

## ADR-006 배포 — 컨테이너 1개 + Postgres

- **상황**: 클라우드·LLM 제공 범위는 교육과정이 아직 안 정함. 인프라 가이드는 '컨테이너 1개 + 관리형 Postgres, 쿠버네티스·큐는 처음엔 안 씀'.
- **결정**: 다단계 Dockerfile(비root), Compose(앱 + postgres:16), 헬스체크, 환경변수 설정. 운영은 같은 이미지를 관리형 컨테이너 서비스에.
- **버린 안**: 쿠버네티스, 메시지 큐, 가상 서버에 직접 설치.
- **결과**: `docker compose up --wait` 한 번에 앱·DB가 healthy, CI가 같은 이미지를 검증. 서비스가 하나라 쿠버네티스의 롤아웃·탐색 기능이 필요 없다.
- **다시 볼 때**: 사내 표준 플랫폼이 쿠버네티스일 때(이미지는 그대로 옮김).

## ADR-007 저장 — SQLAlchemy Core와 덧붙이기 전용

- **상황**: 확정·취소 이력은 수정·삭제할 수 없어야 한다(FR-47). 로컬은 가볍게, 컨테이너·운영은 서버형 DB가 안전하다(여러 인스턴스, 임시 디스크).
- **결정**: SQLAlchemy Core로 표 4개, URL만 바꿔 SQLite ↔ PostgreSQL. 결정·감사·LLM 호출 표는 DB 트리거로 UPDATE·DELETE 금지. 후보 상태는 결정 기록을 다시 읽어 만든다.
- **버린 안**: ORM 모델, 이벤트 스토어 제품, JSON 파일 하나(프로토타입 방식).
- **결과**: 앱 코드에 버그가 있어도 DB가 기록 조작을 막는다(두 DB에서 확인). 실행 결과 JSON을 통째로 넣어 재현은 쉽지만 크기가 크다(타임라인 SVG 포함, 수백 KB).
- **다시 볼 때**: 실행이 많아지면 결과 JSON·보고서는 객체 저장소로, DB에는 요약만.

## ADR-008 화면 — 바닐라 JS와 서버 SVG

- **상황**: FE 담당 2명, 6주. 피그마에 화면 시안은 없고 워크플로우·보고서 양식이 있다.
- **결정**: 빌드 도구 없는 HTML·CSS·JS 한 벌, 피그마 7단계를 단계 막대로. 타임라인은 서버가 SVG로 그려 화면과 보고서가 같은 그림을 쓴다(선박 묶음에 `data-vessel` → 누르면 근거).
- **버린 안**: React·Vue SPA, 차트 라이브러리.
- **결과**: 설치 없이 바로 뜨고 FE가 바로 읽는다. 대신 화면이 커지면 상태 관리가 번거로워진다.
- **다시 볼 때**: 화면이 10개를 넘거나 여러 사용자가 동시에 편집할 때.

## ADR-009 공공데이터 — 제공자와 폴백

- **상황**: 일출·일몰·조석·예보는 공공데이터포털에서 받으라고 했지만 서비스키가 없고, 해양기상관측은 방재 업무용으로 제한된다. 발표 당일 API가 멈추면 안 된다(NFR-10).
- **결정**: 값의 우선순위 = 시나리오에 적힌 값 → 저장해 둔 수집본(`data/public/*.json`) → 오프라인 계산(일출·일몰은 NOAA 태양 위치식). 결과에 출처를 남긴다.
- **버린 안**: 계산 때마다 API 호출.
- **결과**: 키·네트워크 없이 완주. 일출·일몰 오차 1~2분. 조석·예보는 가상 값이라 현업 값과 다를 수 있다.
- **다시 볼 때**: 서비스키를 받으면 `fetch-public`에 수집기를 붙이고 정해진 시각에 돌린다.

## ADR-010 검증 — 두 번 구현해 대조

- **상황**: 과제 원문 "손으로 계산한 정답 세트를 초반에", "같은 코드가 낸 값을 정답으로 쓰면 틀려도 모른다"(09-first-steps).
- **결정**: ① 사람이 손으로 계산한 정답 세트(15종·272칸) ② ETB를 만드는 코드와 다른 방식의 독립 검증기 ③ 6척 이하 완전 탐색 ④ 보고서 숫자 대조 ⑤ 실행마다 검사 10개와 지문. CI는 하나라도 틀리면 막는다.
- **버린 안**: 엔진 단위 시험만.
- **결과**: 개발 중 실제로 잡은 것 — 금액 정규식 쉼표 오류, 한글 파일명 헤더 오류, 화면을 거치며 바뀌는 시나리오 지문, 세 척 사례의 일정 개수(16 → 24) 등. 대조기가 일부러 틀린 정답 3개를 모두 잡는지도 확인했다.
- **다시 볼 때**: 현업 실데이터가 오면 '그때 알던 정보로 다시 계산'(과거 재현)을 정답 세트에 더한다.

## ADR-011 계약 — 계약서를 데이터로 두고 조항을 규칙에 잇는다

- **상황**: v0.1은 선박마다 허용 정박시간·하루 체선료 숫자만 넣었다. 계산은 맞았지만 계산서 근거가 "계약 조건(입력값)"뿐이라, "그 12시간은 어디서 나왔나"에 답할 수 없었다. 체선료는 계약이 정하는 돈이라 같은 대기라도 계약마다 금액이 다르다.
- **결정**: 가상 계약서 23건(`data/contracts/`)을 두고, 한 파일에 사람이 읽는 문서(당사자·Part I·조항·리캡)와 엔진이 읽는 조건(`terms`)을 함께 둔다. 조항마다 엔진 규칙 ID를 적어, 그 규칙으로 계산한 줄에 조항 번호를 붙인다. 계약서에 없는 값만 규칙 표 기본값을 쓴다.
- **버린 안**: 선박에 숫자만 입력(v0.1 방식) / 계약서 PDF를 LLM으로 읽어 조건 추출.
- **결과**: 계산서 9단계 모두 근거가 붙고, 계약 차이(기상 감면 유무, Laycan, 부분 화물 비례, 선적 기한)가 순서를 바꾸는 장면을 시나리오로 보여 줄 수 있다(S08·S14·S15). 대신 계약서 형식을 우리가 정했으므로, 실제 계약서를 넣으려면 변환이 필요하다.
- **다시 볼 때**: 실제 계약서(또는 리캡 메일)를 받을 때 — 그때는 '추출은 LLM + 사람 확인, 계산은 이 형식'으로 나눈다.

## ADR-012 질의응답 Agent를 범위에서 뺀다 (ADR-005의 질의응답 부분을 대신함)

- **상황**: v0.1에는 "왜 1안이 싼가?"에 조회 도구 결과를 인용해 답하는 질의응답 Agent가 있었다. 팀은 11/09 이 기능을 반영하지 않기로 했다.
- **결정**: 화면의 질문 창, `POST /api/runs/{id}/ask`, `agents/assistant.py`, 관련 테스트를 모두 뺀다. LLM은 보고서 문장 한 곳에만 남는다(여전히 선택).
- **버린 안**: 기능은 두고 화면에서만 숨기기.
- **결과**: 같은 질문의 답은 계획 비교 화면('바뀐 것'·'이 안의 근거')과 계산서가 숫자로 직접 보여 준다. 프롬프트 주입·LLM 비용·조회 도구 권한을 관리할 지점이 하나 줄었다. 대화형 탐색의 편의는 잃었다.
- **다시 볼 때**: 현업이 '자유 질문'을 실제로 원할 때 — 그때도 조회 전용·숫자 대조·비용 상한 원칙은 그대로 둔다.

## ADR-013 화면 — SEAGATE 개선 컨셉의 업무형 화면 (ADR-008을 넓힘)

- **상황**: v0.1 화면은 피그마 7단계를 탭으로 옮긴 형태라 '도구 데모'처럼 보였다. 팀 방향은 SEAGATE(Ship Berthing·체선 리포트가 이미 있음)를 개선하는 모듈이다.
- **결정**: 사이드바 6묶음·화면 11개의 업무형 구성, 숫자 타일·부두별 간트·계산서 서랍·계약서 문서 보기. 'Agent'·이모지 같은 도구 말투를 빼고 업무 용어로 쓴다. 간트는 화면에서 HTML로 그리고(마우스 올리기·누르기), 서버 SVG는 보고서·문서에 남긴다. 계속 프레임워크 없이 한 파일.
- **버린 안**: React 등으로 다시 쓰기, SEAGATE 화면을 흉내 낸 디자인.
- **결과**: 첫 화면에서 금액·바뀐 것·근거가 바로 보이고, 계산서에서 계약 조항까지 두 번 누르면 닿는다. 대신 app.js가 한 파일로 커졌다(약 1,000줄).
- **다시 볼 때**: 화면이 더 늘거나 여러 사용자가 동시에 편집할 때 → 컴포넌트 프레임워크로 옮긴다(API는 그대로).

## ADR-014 언어와 서비스 수 — Spring Boot와 Python 두 서비스 (ADR-001을 대신함)

- **상황**: ADR-001은 'Python 하나, 프로세스 하나'였고, 다시 볼 때로 "사내 표준이 Java이거나, 인증·사용자 관리가 커질 때"를 적어 두었다. 11/10 기준 팀 방향은 백엔드 Java/Spring, LLM 쪽 LangGraph다. 예전 핸드오프 문서(5-5)가 제안했던 'Spring Boot API + Python LangGraph Agent' 구조로 돌아가는 셈이다. 팀 6명(AI/DATA 3, BE 2, Infra 1), 마감 12/17. 규모는 한 달 약 100척이고, 요청 한 건에서 계산은 0.3초 안쪽이며(04 문서 5절) LLM 호출은 초 단위다(추정). 서버 언어의 속도는 병목이 아니다.
- **결정**: 서비스를 둘로 나눈다. Spring Boot(Java)가 앞단에서 로그인·권한·승인·감사·업무 데이터를 맡는다. Python 서비스가 LangGraph와 계산 엔진을 맡고, 지금 demo 이미지를 이어 쓴다(ADR-001 '다시 볼 때'에 적어 둔 길). Python 서비스는 밖에 열지 않고 Spring만 부른다. 계산 엔진은 Java로 옮기지 않는다 [팀 확인 필요].
  - 고른 이유 [팀 확인 필요 — 실제 이유에만 표시하고 나머지는 지운다]
    - [ ] BE 2명이 Java/Spring에 익숙하다
    - [ ] 교육과정이나 운영 주체의 표준이 Java다
    - [ ] 인증·사용자·권한 관리가 커졌다
  - 일반론: 로그인·권한·트랜잭션·검증·헬스 점검이 Spring에 기성품으로 있고, 국내 기업 시스템에서 흔해 넘겨받는 쪽이 유지보수하기 쉽다(추정). LangGraph와 기존 엔진·검증기는 Python이라 그쪽은 그대로 둔다.
- **버린 안**:
  - *Python 하나(ADR-001 그대로)*: 서비스 사이 직렬화·배포·장애 지점이 없어 인프라가 가장 단순하다. 이 안을 버린 값이 아래 '잃은 것' 전부다.
  - *Go*: 작고 빨리 뜨는 실행 파일과 동시성이 강점이라 인프라 도구나 트래픽 많은 서버에 맞다. 로그인·권한·트랜잭션은 라이브러리로 직접 조립해야 하고, 우리 병목은 처리량이 아니다.
  - *Rust*: 성능과 메모리 안전이 강점이고 CPU가 병목인 엔진·프록시에 맞다. 배우는 비용과 개발 속도 손해가 큰데, 우리 요청의 시간은 LLM이 쓰므로 얻는 것이 없다.
  - *전부 Java(Agent도 Spring AI 등으로)*: 런타임이 하나가 된다. 대신 Python 엔진·독립 검증기·정답 세트(시험 88개, 272칸)를 다시 써야 한다.
- **결과**: 얻은 것 — 인증·권한을 직접 만들지 않는다. LLM이 붙은 서비스가 인터넷에 직접 닿지 않는다. 엔진과 정답 세트를 그대로 쓴다. 잃은 것 — ADR-001이 피했던 '서비스 경계를 넘는 비용'을 치른다. 이미지 2개, CI 줄 2개(Gradle·JUnit / pytest), 서비스 사이 통신과 버전 맞추기(ADR-015), 장애 지점 하나가 늘고, 로컬에서도 Compose가 있어야 전체가 뜬다. ADR-005와의 관계 — LangGraph를 '그래프 실행기'로 쓰는 것은 ADR-005가 버린 '자율 멀티 Agent'와 다르다(03 문서 2절: 노드만 감싸면 된다). LLM이 도구를 골라 흐름을 정하게 할지는 아직 정하지 않았고, 정하면 새 번호로 덧붙인다.
- **다시 볼 때**: 서비스 사이 호출 때문에 개발이 계속 느려질 때(한 언어로 합치기를 검토), 계산 엔진을 Java 쪽에서 직접 돌려야 하는 요구가 생길 때.

## ADR-015 서비스 사이 통신 — REST와 SSE

- **상황**: 서비스가 둘이 되면서(ADR-014) Spring이 Python 서비스를 부르는 길이 생겼다. 호출 경로는 하나(Spring → Agent)이고 하루 수십~수백 건 수준이다(인프라 가이드, 추정). 엔진 API는 이미 REST·JSON이다(`POST /api/runs`, 02 문서). LLM 호출과 문서 파싱은 초 단위 이상 걸려(추정) 한 번의 요청·응답으로 끝나지 않을 수 있다. 질의응답은 범위에서 뺐으므로(ADR-012) 화면으로는 서버가 진행 상황을 보내기만 하면 된다.
- **결정**:
  - Spring → Agent는 HTTP 위의 REST(JSON)로 부른다. FastAPI가 만드는 OpenAPI 명세를 두 서비스의 계약으로 삼고, 경로에 버전(`/v1`)을 둔다.
  - 오래 걸리는 일은 작업 ID를 먼저 돌려주고 상태를 조회한다. 진행 상황을 화면에 흘려야 하면 SSE를 쓴다.
  - Spring이 만든 요청 ID를 헤더로 넘겨 두 서비스 로그에 같이 남긴다.
  - 브라우저는 Spring만 부른다. Agent 주소는 내부에서만 보인다.
- **버린 안**:
  - *gRPC*: 계약 파일(`.proto`)에서 양쪽 코드를 만들어 타입이 어긋나지 않고, 빠르고, 양방향 스트리밍이 된다. 대신 빌드 도구가 두 벌(Gradle, Python) 늘고, 눈으로 요청을 확인하기 어렵고, 로드밸런서에 HTTP/2 설정이 필요하다. 호출 경로 하나에는 이득이 작다.
  - *메시지 큐(SQS, Kafka)*: 재시도와 완충, 느슨한 결합을 얻는다. 대신 운영할 것이 늘고 한 요청을 따라가기 어려워진다. 인프라 가이드 4-3·7장도 '큐는 나중에'다.
  - *웹소켓*: 양방향이 필요할 때 쓴다. 지금은 한 방향이라 SSE로 충분하다.
  - *같은 DB 표를 둘이 읽고 쓰기*: 계약이 코드 밖에 숨어, 한쪽의 스키마 변경이 다른 쪽을 조용히 깨뜨린다. DB는 하나를 쓰되 스키마를 나눈다.
- **결과**: 얻은 것 — `curl`과 브라우저로 바로 확인하고, 기존 엔진 API를 그대로 쓰며, Compose와 로드밸런서 어디서나 같은 방식으로 돈다. 잃은 것 — 타입 계약이 gRPC보다 약해 OpenAPI와 계약 시험으로 메워야 한다. SSE는 중간 장비의 유휴 타임아웃에 끊길 수 있어 하트비트가 필요하다. Agent가 도구를 부르는 길(MCP 등)은 이 결정의 범위 밖이다.
- **다시 볼 때**: 문서 파싱 같은 작업이 밀리거나 실패 재시도가 중요해질 때(큐), 내부 서비스가 셋 이상으로 늘어 호출이 얽힐 때(gRPC), 화면에서 대화형 입력이 생길 때(웹소켓).

## ADR-016 EKS 배포 준비 — 제공받은 클러스터와 팀 자원의 경계

- **상황**: 2026-11-11 사용자가 다음 주 IAM 접근·EKS·S3 등 AWS 자원 제공을 예상하며 YAML·CronJob·Terraform 사전 준비를 요청했다. ADR-006의 관리형 컨테이너 배포 방향을 EKS에 구체화한다. 실제 제공 범위와 생성 권한은 아직 확정되지 않았다.
- **결정**: 현재 Python 데모 이미지로 내부 API Deployment·Service와 보고서 CronJob을 구성한다. PostgreSQL은 외부 DB를 사용한다. Terraform은 기존 EKS를 조회하고, S3·ECR·배치 IAM/Pod Identity는 팀 담당 범위에 따라 선택적으로 관리한다. 클러스터·VPC·노드·RDS를 새로 생성하지 않는다. CronJob은 수동 검증 후 활성화한다.
- **이유**: 실제 실행 코드와 정답 검증을 재사용하고, 공유 인프라 소유권과 팀 앱 배포 책임을 분리한다. 다음 주에는 접속 정보·이미지 주소·버킷·DB 값을 채워 연결을 검증할 수 있다.
- **결과**: 초기 API 1 replica/Recreate는 DB 시작 DDL 경합을 줄이지만 무중단·고가용성 배포는 제공하지 않는다. 현재 배치는 이미지의 가상 시나리오 보고서이며 실제 수집·확정·발송을 수행하지 않는다. ADR-014·015의 Spring Boot/LangGraph 분리 방향은 유지하고 구현이 준비되면 별도 Deployment를 추가한다.
- **다시 볼 때**: 제공 자원의 실제 권한·노드 방식이 확인될 때, 마이그레이션을 분리할 때, Spring Boot·실제 입력 수집 구현이 준비될 때. [설정 이유와 역할](../14-eks-architecture.md), [배포 절차](../../deploy/README.md).
